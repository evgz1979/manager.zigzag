# Хранение и восстановление данных

Версия: **2.106.0**. Обновлено: **28 октября 2026 года**. Статус: **текущее хранение; обмен с iPhone отложен**.

Отметка календаря «Выполнено» независима от актуальности: `orders.extra_blocks["Выполненные события календаря"]` содержит JSON `{"version":1,"day":["2026-10-27"],"week":[]}` с отсортированными уникальными датами, неделя — понедельник. API ответа `calendar_completed`; отсутствие блока означает пустые отметки, неизвестный формат — `null` без перезаписи. Свободные события получают `calendar_events.is_completed INTEGER NOT NULL DEFAULT 0`; при добавлении столбца пересоздаются аудит-триггеры, прежние строки сохраняются без изменения версий и текстов. Планы используют `_calendar_completed` в прежнем `invoices.data`, без нового поля таблицы. `/api/order-calendar-completed`, `/api/calendar-completed`, `/api/invoice-plan-calendar-completed` принимают строгий boolean `is_completed`, UUID и обязательную целую revision, для заказа также путь, дату и период. Одна частичная транзакция повышает версию и сохраняет metadata_history/invoice_history; дата сортировки заказа, тексты, деньги, номера, статусы, цвет, актуальность и прочие поля сохраняются. Перенос переносит отметку, правка её сохраняет, удаление и отмена удаления восстанавливают вместе с событием. Конфликт, отсутствие записи, корзина и неизвестный формат не заменяют данные. Первый выбор/снятие ставит `metadata_settings.calendar_event_completion=1`; откат без `CALENDAR_COMPLETION_VERSION = 1` блокируется. Новых файлов и чтения iCloud нет. Выполненные дневные события исключены из оснований показа строки и диапазона; выбранный срок оставляет строку. Правило общее для обычных заказов, поставщиков и PNG. Свободные события и планы остаются видимыми серыми с галочкой; это не оплата и не выполнение заказа.

Обнаружение счетов, вручную добавленных в непосредственную `# bills` клиентского заказа: отдельный `/api/invoice-folder-candidates` читает только имена/метаданные при открытии карточки и по «Проверить # bills», без BLOB и импорта. Опрос `/api/invoices` остаётся SQLite-only. Известные filename счетов и invoice_documents, включая корзину и удалённые связи, скрытые файлы, вложенные папки и ссылки исключены. После явного подтверждения `/api/invoice-folder-attach` проверяет регистрацию, путь, отпечаток файла до/после ограниченного по времени чтения Foundation/iCloud, размер до 20 МБ и завершённость PDF. Создаёт прежний external в invoices с неизменяемым BLOB, исходными filename/data.original_name и exported=1: существующий файл остаётся на месте, второй PDF не публикуется. Детерминированный UUID и транзакционная проверка точных PDF-байтов того же заказа защищают от дубля после потери ответа и одновременного подтверждения; поздний комментарий/версия сохраняются, корзина не восстанавливается. Новых таблиц и миграций нет; карточка, нумерация, финансы и статусы заказа прежние.

## Где находится информация

По решению пользователя рабочая информация хранится преимущественно в локальной SQLite на M4. В Finder пользователь смотрит исходные файлы и выпущенные документы. Прежнее требование читать всю карточку из папки отменено. Файлы `!.txt` и скрытые комментарии теперь являются источниками первоначального переноса, а не актуальными копиями базы.

| Информация | Рабочий источник | Что находится в каталоге документов |
| --- | --- | --- |
| Регистрация, название, статусы, финансы, заметка заказа | `orders` в SQLite | Прежняя карточка остаётся без обновления |
| Заметки любых папок, собственные To-do, дополнительные блоки | `folder_notes` в той же SQLite | Прежние карточки остаются без обновления |
| Избранное, закупки, поставщики, актуальность событий и CDR | Дополнительные блоки записей SQLite | Новые служебные файлы не создаются |
| Цвета разделов-поставщиков `# work` | `metadata_records`, вид `work_supplier_color`, путь раздела | Файлы не создаются |
| Звёзды разделов `# work` и их порядок | `metadata_records`, вид `work_supplier_favorite`, путь раздела; начальная настройка `work_supplier_favorite_defaults` по пути корня | Файлы не создаются |
| Подборки заказов поставщиков в заказах корня `# work` | Блок «Связанные заказы поставщиков» в `orders.extra_blocks`, UUID заказов | Папки остаются на местах, новые файлы не создаются |
| Неактивность клиентов и объектов | `client_activity`, `object_activity` | Прежние отметки используются только при первом переносе |
| Комментарии к файлам | `metadata_records`, вид `comment` | Оригинал файла не меняется; старые `.file-comments` сохраняются |
| Черновики заданий на печать | `metadata_records`, вид `print` | Файл появляется только при выпуске |
| Счета, договоры, реквизиты, нумерация, история, выпущенные PDF | Таблицы счетов в SQLite | Неизменяемые копии выпущенных PDF в `# bills` |
| Выпущенные задания на печать | Неизменяемое содержимое в `metadata_publications` | Отдельный TXT с названием, ссылкой и описанием |
| Фотографии, видео, макеты, входящие документы | Исходные пользовательские файлы | Остаются на прежних местах |
| PDF-отчёты по изображениям | Готовый PDF | В открытой папке, без изменения оригиналов |
| История правок и исходные байты переноса | `metadata_history`, `legacy_documents` | Прежняя история также остаётся нетронутой |

База — `data/orders-<root-hash>.sqlite3` в общей папке установки `/Volumes/nvme2Tb/manager.zigzag` на M4. Корень документов задаётся в `manager.ini`; другой корень получает отдельную базу. `data/` не синхронизируется через iCloud и не входит в обычный пакет кода. Доступ с других компьютеров идёт через сервер M4.

## Настройки отправки календаря

Кнопка «В Telegram» отправляет снимок текущей и следующей недель в твой личный чат отдельного бота менеджера. Отправка через actu отключена. PNG существует только в памяти браузера и запроса, в SQLite и каталогах документов не сохраняется. Источники календаря и все рабочие данные остаются прежними.

Секреты отдельного бота — локальный `data/telegram.ini` M4, права `0600`, секция `[telegram]` с `purpose = manager-calendar`, `bot_token`, `chat_id` и `bot_username`; путь можно задать `MANAGER_TELEGRAM_SETTINGS`. Это техническая настройка сервиса, вне рабочей SQLite, Git, пакетов релизов, документов и ежедневного ZIP. Обычный деплой и откат её сохраняют. Прежняя копия токена actu сохранена отдельно в `data/telegram-actu-disabled.ini` с правами `0600` и не используется для отправки; она позволяет отклонять повторное подключение того же бота. Исходные настройки actu не меняются. При восстановлении с ZIP подключи отдельного бота заново через окно менеджера. Токен вводится пользователем в скрытое поле, передаётся только серверу M4 для проверки и атомарного сохранения, не возвращается в ответах API и не пишется в логи; закрытие окна очищает поле. Поиск получателя не сохраняет тексты сообщений. [Подключение](operations.md#снимок-календаря-в-telegram).

## Перенос прежних данных

Перед переносом создаётся согласованная резервная копия SQLite. Фоновый обработчик проходит обычные папки, включая производственные и финансовые разделы. Читает только служебные карточки, комментарии, прежние задания на печать и их историю; содержимое обычных вложений не читает. Ссылки и скрытые поддеревья пропускает, кроме явно известных каталогов истории.

Существующие записи SQLite всегда имеют приоритет. Отсутствующая заметка или комментарий импортируются при первом открытии либо в фоне. До разбора файла точные исходные байты сохраняются в `legacy_documents` с путём и SHA-256. Поддержаны `!.txt`, прежние `!status.txt`, `!order.txt`, `.order.json`, `status.txt`, `.status.txt`, `.file-comments`, `.order-history`, `.print-history` и история комментариев. Неизвестные дополнительные блоки сохраняются.

Успешно перенесённые данные больше не перечитываются из прежних файлов. Новые записи и очищенные значения остаются в базе; старая карточка не возвращает удалённые задачи или комментарии. При обычной миграции исходные файлы не удаляются и не перезаписываются. По отдельному решению пользователя от 23 октября 2026 года уже перенесённые `!.txt` разрешено убрать из рабочих папок в скрытый восстанавливаемый архив; условия и выполненная операция описаны ниже. Существующий `!.txt` имеет приоритет среди старых форматов, но не над рабочей базой.

Ошибка iCloud не превращается в пустое значение. В `metadata_imports` остаются путь и ошибка, перенос повторяется через 60 секунд и после запуска. Состояние и первые ошибки видны под таблицей заказов; «Повторить перенос / выпуск» запускает повтор. Чтение прежних файлов использует `icloud_access.py` и согласованное чтение Foundation с таймаутом. Ошибка одного файла не останавливает остальные. Пока перенос конкретного комментария не завершён, его замена отклоняется с сохранением ввода в браузере.

## Архив устаревших карточек

После явного разрешения пользователя можно убрать `!.txt` из рабочих каталогов, если для каждой папки подтверждены рабочая запись `orders`/`folder_notes` и успешный первоначальный перенос. Сравнение путей учитывает NFC; похожие имена не объединяют. Перед файловыми действиями проверяется отсутствие прерванных переносов, создаётся проверенный снимок SQLite, все текущие точные байты сохраняются в `legacy_documents` под текущим путём и SHA-256. Существующие карточки, заметки, финансы, задачи, неизвестные блоки и очереди не переписываются старыми значениями.

Оригиналы переносятся без перезаписи в `.folder-layout-history/.legacy-cards-<сеанс>/.cards/`; журнал хранит исходные пути, идентичности, размеры и хеши, план и самостоятельный `.restore.py` с помощником согласованного чтения iCloud. Намерение операции фиксируется в SQLite до переносов. Перед каждым переносом заново проверяются путь, отсутствие ссылок, идентичность, байты и блокировки. Откат возвращает только эти файлы, не заменяет базу, сохраняет новые данные и останавливается при занятом пути или изменённом оригинале. При обрыве тот же план позволяет вернуть уже перемещённую часть. Автоочистки нет; другие прежние форматы и история остаются на месте.

23 октября 2026 года на M4 таким способом убраны 104 файла (40 987 байт), сеанс `.legacy-cards-20261023T064804Z-d3fb5f5a`. Проверены отсутствие `!.txt` в открытых рабочих каталогах, точные копии всех файлов в SQLite и возможность восстановления всех 104 файлов. Таблицы заказов, заметок, счетов, выпусков и прочие записи метаданных совпали со снимком до операции; ошибок переноса нет.

## Локальная база миниатюр

По решению пользователя от 25 октября 2026 года миниатюры хранятся **рядом с рабочей базой M4**, в `data/thumbnails-<хеш корня>.sqlite3`, с WAL/SHM в том же локальном каталоге. В папке «Зигзаг», iCloud или рядом с оригиналами кеш не создаётся. У каждого корня документов свой кеш, тестовые и рабочие данные не смешиваются. Это технические JPEG до 640 пикселей, которые можно получить заново; они не входят в ежедневный ZIP рабочей базы.

Отдельный процесс обходит видимые каталоги, сохраняет относительный путь, идентичность файла, размер, время изменения, миниатюру и состояние повтора. Он не создаёт заказов, не читает карточки для регистрации, не меняет структуру или байты исходников. Ссылки, скрытые папки, истории и резервные CDR пропускаются. Открытая папка ставит свои файлы в приоритет. Картинки, первые страницы PDF и кадры видео обрабатываются локальными средствами macOS; CDR используют встроенное PNG/BMP, прочие поддерживаемые документы — Quick Look при наличии провайдера формата.

Исходники получает отдельный помощник через Foundation и `NSFileCoordinator`, с загрузкой iCloud и временной локальной копией. Результат публикуется только при неизменной идентичности/размере/mtime исходника и совпадении ключа очереди. Ошибки повторяются через 60 секунд с увеличением паузы до часа; повторное открытие страницы не сбрасывает паузу. Ошибка обхода папки не удаляет прежние готовые миниатюры. После успешного обхода отсутствующие пути помечаются `missing`, изменившиеся файлы пересоздаются. Между обходами кеш может кратко показывать прежнюю версию; уже известное изменение не выдаёт старую картинку за новую.

`/api/thumbnail`, `/api/thumbnail-cover`, `/api/thumbnails` и `/api/thumbnail-status` работают только с локальным кешем, без чтения или проверки исходников в iCloud. Страница опрашивает состояние раз в пять секунд и заменяет только изображения. Полный просмотр/воспроизведение и скачивание оригинала по-прежнему требуют доступа к самому файлу.

## Карточки, заметки и задачи

Создание заказа через менеджер сразу создаёт запись `orders` в том же запросе. Название — из формы без даты; начальные статусы «Новый» / «Не указан», остальные поля пустые. Это относится к объектам, годовым группам, корню `# work`, производственным и финансовым разделам. Вся ветка `# work` остаётся вне обычного списка главной. Прежние и вручную созданные папки требуют отдельного добавления; открытие папки, создание объекта и события не регистрируют заказ.

Кнопка массового поиска «Найти заказы в папках» убрана из интерфейса вместе с подсказками о ней. Прежнюю или вручную созданную папку заказа добавляют через её карточку кнопкой «Добавить в список заказов». Совместимость первоначального переноса прежних данных сохраняется.

Перед созданием каталога в `metadata_records` сохраняется намерение вида `order_creation`, путь, UUID заказа, название и журнал. После подтверждённого создания карточка и состояние `complete` фиксируются одной транзакцией. Незавершённая регистрация повторяется после запуска, каждые 60 секунд и по явной кнопке добавления, с тем же UUID. Сверяются журнал и идентичность каталога, прежние карточки и чужие папки не заменяются. Файловый откат блокирует удаление папки, если её карточка сохранена в SQLite; обычное снятие регистрации сохраняет данные.

Список заказов, фильтры и сохранение уже перенесённых карточек, заметок и комментариев используют SQLite. Загрузка самих папок и списка файлов по-прежнему зависит от доступности документов. Готовые миниатюры читаются из отдельного локального кеша без обращения к iCloud. Сохранение метаданных не требует чтения содержимого оригиналов или записи `!.txt`.

Заметки любых папок хранятся отдельно от регистрации заказа. События, материалы, `#…`, клиенты, объекты и группы получают запись `folder_notes`, но не становятся заказами автоматически. У заказа собственные задачи находятся в дополнительных блоках `orders`; у вложенных папок — в их `folder_notes`. Клиентам, объектам, годам и служебным папкам вне заказа редактор To-do не показывается. Снятие регистрации сохраняет поля и задачи; повторное добавление явно восстанавливает запись базы.

После добавления в общий список редактор переключается с `folder_notes` на `orders` сразу, без повторного открытия папки. Сохранение и фоновый опрос используют карточку заказа; старый редактор черновика отклоняется сервером, ввод остаётся в поле.

Сохранение проверяет версию; устаревшая вкладка не заменяет новые данные. Прежние значения карточек, заметок, активности и комментариев фиксируются триггерами в `metadata_history` в той же транзакции, включая изменения путей при самостоятельном откате. История не является отдельной резервной копией.

To-do содержит текст и отметку выполнения. В основном заказе показываются задачи всех вложенных папок на любой глубине; собственный редактор остаётся отдельным. На главной — только невыполненные задачи с группировкой по папкам. Сводка читается из SQLite. Фоновый `order_todos.py` обновляет каталог путей при запуске, через 5 минут и по кнопке «Обновить To-do»; ещё не перенесённые карточки импортируются при необходимости. Обычные вложения не читаются.

Отсутствие пути при полном успешном обходе записывается в `todo_missing_folders`: задачи скрываются из окна, счётчика и поиска, сами записи сохраняются. Неполный обход не объявляет неувиденные пути удалёнными. Повторно появившаяся папка возвращается. Похожие имена и одинаковые задачи не являются основанием объединять записи.

## Закупки у поставщика

Заметка слева и сводка закупок справа используют прежние данные и операции. Двухколоночная компоновка включается только при видимом блоке закупок, не создаёт настроек или записей в SQLite и не затрагивает ввод заметки.

Каждая закупка в сводке поставщика или `etc` отображается одной строкой вместе с чекбоксом и ссылкой на исходный заказ. Отдельные строки заголовка и пути заменены подписью источника справа и полными title/доступными именами; длинные подписи сокращаются многоточием без изменения текста. Формат API, хранение, версии, история и правила выполнения/распределения прежние. Опрос сохраняет фокус чекбокса или ссылки, прокрутку и ввод других форм.

`etc` — вычисляемая подборка того же источника: выбранные поставщики строки не пересекаются с фиксированным набором `antares`, `himlex`, `newtek`, `glass`. Пустой выбор и TBM/Remex без основного включаются; строка с хотя бы одним основным исключается. Одна и та же проверка используется при чтении и частичной записи выполнения, поэтому назначение основного поставщика блокирует устаревший запрос из etc. В исходных строках не создаётся поставщик `etc`, новых полей и копий задач нет. Неизвестные форматы по-прежнему не интерпретируются и не заменяются.

Первая группа включает существующий etc прежним `work_supplier_favorite` с UUID, версией и историей. Сортировка кнопок и групп заказов ставит etc последним независимо от сохранённой позиции, не переписывая другие позиции. Известный `work_supplier_color` только etc получает `neutral=true`, с прежними UUID и hue, повышением версии и историей той же транзакцией; снимок перед обновлением находится в обычной истории деплоя M4. Повторное чтение версию не меняет. Новый etc сразу получает нейтральный цвет; прочие цвета и неизвестные записи сохраняются. Формат метаданных и схема прежние.

`supplier_purchases.py` вычисляет To-do поставщика из `purchase_items` зарегистрированных обычных заказов. Источник один — прежний блок `orders.extra_blocks["Закупки и затраты"]`; копий в `Задачи`, новых UUID строк, таблиц или полей нет. Путь непосредственного раздела `# work` сопоставляется с точным именем выбранного поставщика без `#`, пробела и регистра; поддерживается прежняя корневая `# glass`. Все статусы включены, неактивные клиенты/объекты и снятые регистрации исключены. Производство и финансовые разделы источниками не являются. Неизвестные блоки не интерпретируются и не заменяются.

`GET /api/supplier-purchases` читает только SQLite и возвращает группы исходных заказов с путём, UUID, версией и индексами подходящих строк, включая выполненные. Интерфейс по умолчанию скрывает выполненные и раскрывает их по переключателю. Снятие выбора поставщика, удаление строки или регистрации убирает её из представления при следующем опросе, без отдельных копий и синхронизации данных.

`POST /api/supplier-purchase-done` требует `supplier_path`, `path`, `id`, целые `revision` и `index`, исходный `text` и логический `done`. Проверяются обычный зарегистрированный источник, текущий выбор поставщика, формат и блокировки путей. Меняется только символ чекбокса выбранной строки прежнего текста блока; пробелы, переводы строк, другие строки и поставщики сохраняются. Одна версия и запись истории той же транзакцией; `updated`, деньги, статусы, заметка, обычный To-do и остальные блоки не меняются. Две одинаковые строки различаются индексами в обязательной версии; после перестановки старый запрос отклоняется. Конфликт и ошибки ничего не заменяют, автоматического повтора записи нет. Общая отметка видна в исходном заказе и у всех выбранных поставщиков.

Опрос блока поставщика не заменяет заметку или другие формы. Исходная открытая карточка принимает частичное изменение закупок только при неизменности остальных полей, без несохранённого ввода и фокуса в редакторе закупок; иначе сохраняет прежнюю версию для явного разрешения конфликта. Схема, документы и прочие данные производства сохраняются.

## Список заказов производства

Собственный статус распространяется и на прямые датированные заказы `# work`. Переход в архив атомарно сохраняет UTC ISO-время с микросекундами в `extra_blocks["Дата архива заказа производства"]`. Повтор статус не датирует заново, выход сохраняет метку, повторный вход обновляет. Неизвестная дата не заменяется. Старым архивам момент последнего перехода вычисляется по `metadata_history` без записи.

`/api/work-orders` возвращает активные `orders`, все `archived_paths` для скрытия плиток и до 10 `archived_orders`, по времени архивирования и последовательности истории. Область — прежний текущий список поставщика или корня. Возврат меняет статус на `work` прежним API с UUID/версией; основной список снова использует `folder_date`. Документы, связи, остальные данные и схема SQLite сохраняются.

`folder_date` вычисляется только из последнего компонента сохранённого пути существующим `folder_structure.DATE`/`dated`: `YYYY-MM-DD`, короткий год превращается в 20xx, частичные даты с 00 сохраняются. Значение не записывается в SQLite и не заменяет `updated`. API и начальная сортировка таблицы используют убывание этой даты; отсутствующие/некорректные даты в конце, равные — по пути и UUID, без приоритета избранного или собственной подписи карточки. Группы поставщиков корня прежние. В интерфейсе «Дата заказа» заменяет «Обновлён» только для производства; главная и объект сохраняют прежнее поведение.

Статус обычного заказа поставщику хранится отдельно от прежних `status`/`financial_status` в `orders.extra_blocks["Статус заказа поставщику"]`: строки «В работе», «Отменён», «В архив». API возвращает `supplier_status` с ключами `work`, `cancelled`, `archived`; отсутствие блока вычисляется как `work` без записи. Неизвестное значение возвращается как null, не скрывается и не заменяется. Печать, фрезеровка и прямые заказы корня вне этого правила.

`POST /api/order-supplier-status` требует путь, UUID и целую revision зарегистрированного заказа. Меняет только этот блок, повышает версию и пишет историю той же транзакцией; `updated`, скрытые прежние статусы, деньги, сроки, заметки и остальные блоки сохраняются. Полное сохранение карточки принимает `supplier_status` в прежней транзакции. Неверная область, значение, версия, UUID, блокировка или неизвестный формат оставляют запись без изменений. В старом файловом режиме блок защищён от замены устаревшим экспортом.

Архив — вычисляемое исключение из списков поставщика/корня, избранного и подборок, не удаление регистрации или каталога. Сохранённые UUID связей остаются, новые архивные связи запрещены; возврат возвращает прежний показ. Дерево, прямой API карточки и календарь сохраняются. Отмена остаётся видимой. Новых таблиц, колонок и миграций нет.

Тот же каталог и `/api/work-orders` обслуживают отдельные разделы поставщиков `# work`, включая `etc`, и прежнюю корневую `# glass`. В scope раздела входят только его непосредственные обычные папки, независимо от избранного. Печать и фрезеровка исключены из этой таблицы. Используются прежние виды `work_orders_scope`/`work_order_folder` без новой схемы. При полном чтении `present=false` получают только отсутствующие пути проверенного scope: открытие корня не очищает каталог непроверенного раздела без звезды, а чтение раздела не затрагивает соседей. Опрос, версии карточек, заметки, сроки, финансы, документы и регистрация сохраняют прежние правила.

`work_order_list.py` использует общий каталог таблицы для корня `# work`: непосредственные заказы отмеченных звёздами разделов и датированные заказы самого корня. При открытии и по «Обновить» читаются только имена папок до границы заказа, без содержимого вложений, событий, ссылок и автоматической регистрации. В прежней таблице `metadata_records` используются виды `work_orders_scope` и `work_order_folder`, формат 1, UUID, версии и история по тем же правилам каталога объекта. Ошибка чтения сохраняет последний каталог; полный обход скрывает подтверждённо отсутствующие незарегистрированные папки. Неизвестные форматы не заменяются.

`/api/work-orders` обновляет строки и порядок групп только из SQLite; текущие звёзды разделов определяют видимость заказов. Снятие звезды не меняет заказы, возврат возвращает сохранённые строки; новые папки выбранного раздела обнаруживаются при открытии или «Обновить». Незарегистрированные папки используют сохранённые рабочие записи или заметки SQLite и не становятся заказами автоматически. Маркеры и сроки сохраняются прежними частичными операциями. Статусы, финансы, закупки и документы сохраняются без изменений; в обычные списки главной производство по-прежнему не входит. Редактор заметки корня скрыт без удаления её данных. Новых таблиц и миграций нет.

## Список заказов объекта

Главная и объект используют один компонент таблицы и обработчики поиска, фильтров, сортировки, избранного, To-do, закупок, статуса, сроков и итогов. На главной остаются три группы. В объекте начальный фильтр «Все», четвёртая группа определяется тем же правилом скрытия статусов главной (сейчас «Отменён» и «Готово») и дополнительно содержит все незарегистрированные папки заказов с отметкой «Не добавлен», независимо от их сохранённого статуса. Пустые группы скрыты. Заметка объекта и его неактивность сохраняются; обновление таблицы не перезаписывает ввод.

При открытии объекта и по «Обновить» `object_orders.py` просматривает только имена каталогов объекта, включая годы и вложенные контейнеры, до границы заказа. События, служебные ветки и ссылки не обходятся; содержимое вложений и прежние карточки не читается. В `metadata_records` сохраняются записи `object_orders_scope` по пути объекта (версия формата 1, время проверки и ошибка) и `object_order_folder` по пути найденной папки (версия формата 1, признак присутствия). Используются обычные UUID, обязательные версии и история метаданных. Неизвестный формат сохраняется без замены. При неполном обходе прежние пути остаются; полная проверка скрывает подтверждённо отсутствующие папки без удаления данных. Зарегистрированные записи SQLite остаются доступны при недоступности папок.

Фоновый `/api/object-orders` читает только SQLite: зарегистрированные `orders` и кеш имён папок; для папки без регистрации — сохранённую рабочую запись `orders`, а при её отсутствии черновик `folder_notes`. Имена кеша и рабочие пути сопоставляются в NFC, чтобы эквивалентная запись букв не создавала вторую строку «Не добавлен»; исходный путь, UUID, версия и данные рабочей карточки не меняются. Разные записи базы не объединяются. Новые папки вне менеджера появляются после открытия объекта или «Обновить». Это не поиск и не импорт прежних карточек, автоматической регистрации нет. Звезда, статус и сроки незарегистрированной строки недоступны для записи; её можно открыть и явно добавить через карточку. Переименование, группировка по годам и самостоятельный откат согласуют ключи каталога обычным переносом путей `metadata_records`; вложенные пути в данных кеша не дублируются.

## Статусы и деньги

«Скрытые заказы» — вычисляемый показ `/api/hidden-orders` из клиентских `orders` (включая снятые регистрации), отметок `client_activity`/`object_activity` и известных папок `metadata_records` вида `object_order_folder`, дополненных сохранённым черновиком `folder_notes`. Вся ветка `# work` и прежняя корневая `# glass` исключены по пути до вычисления причин; `work_order_folder` не читается. Производственные заказы, черновики, архив и предупреждения их каталогов на страницу не попадают. Новых таблиц, полей, файлов данных и миграций нет. Неизвестный клиентский каталог пропускается с предупреждением, без замены данных. Папки без сохранённого каталога автоматически не обнаруживаются. Группы используют полные пути клиента и объекта. Сворачивание хранится только в localStorage `zigzag.hidden-orders.collapsed.v1`.

Производство и оплата — независимые ручные поля. Финансовые статусы: «Не указан», «На оплате», «Частично оплачен», «Оплачен». Производственный этап «На оплате» (`awaiting_payment`) добавлен после `process` в первую группу; в карточке и таблицах имеет зелёный текст `#2f7d46` на фоне `#e1f1e5`. Сохраняется прежними операциями в `orders.status`, с версиями и историей, без миграции или массового изменения записей. Его выбор не меняет `financial_status`, суммы или счета. Прежний смешанный «На оплате» (`payment` либо текст старой карточки без отдельного финансового статуса) по-прежнему переносится в финансовое поле. При чтении современной карточки с отдельным финансовым статусом одноимённый производственный этап сохраняется независимо от оплаты. Ключ `process` называется «Расчеты», прежнее «В работе» принимается при импорте. «Жду» (`waiting`), «Предложить позже» (`offer_later`), «Отложен/возможно», «Переделка/доделка», «Завершение/добивка» и «Готово, но…» сохраняются как самостоятельные этапы.

Смена производственного статуса в строке главной выполняется отдельной частичной операцией `/api/order-status`: обязательная версия показанной строки, обновление только `status`, `revision`, `updated` и технического состояния синхронизации. История сохраняется в `metadata_history` той же транзакцией. Остальные поля карточки и дополнительные блоки, включая неизвестные, не заменяются. Чтение и сохранение работают без iCloud. Конфликт версии, снятая регистрация и заблокированный путь отклоняют запись.

Суммы хранятся целыми копейками, ввод — неотрицательные рубли с двумя знаками. Прибыль и остаток оплаты вычисляются из суммы, затрат и оплаты. Изменение денежных сумм не меняет статусы. Блок «Фильтры и итоги» и его статусные/финансовые фильтры убраны из общей таблицы главной и объекта без изменений данных, версий или истории. Строковые финансовые колонки и редакторы сохраняются. Основной список скрывает «Отменён» и «Готово»; их просмотр — на отдельной странице «Скрытые заказы» или в таблице объекта.

В заказах всей ветки `# work` карточка в интерфейсе содержит только название и заметку. Производственный и финансовый статусы, их значки, суммы и расчёты скрыты. Сохранение названия, заметки и задач оставляет прежние значения статусов и финансов в SQLite: скрытые поля инициализируются из загруженной карточки и сохраняются с той же проверкой версии. To-do и подборки остаются отдельными блоками. Обычные карточки вне `# work` сохраняют полную форму.

## Сроки по неделям

Видимая область календаря вмещает две полные недели; высота равна сумме их фактических высот вместе с шапками оплат. Отдельная неделя сохраняет прежнюю базовую высоту. Стрелки сдвигают на неделю, Home/End показывают первую/последнюю пару; заголовок и aria-label охватывают 14 дней. Минимальный диапазон и PNG для Telegram — текущая и следующая недели по Москве, без сокращения доступного диапазона сохранённых данных. Это только отображение и снимок, без записи SQLite или изменения форматов.

Неактуальные дневные события исключаются только из оснований показа строки заказа и расчёта диапазона календаря. Неделя показывается для заказа при выбранном сроке или хотя бы одном актуальном дневном событии; остальные недели того же заказа оцениваются независимо. Если строка остаётся по другому основанию, все её сохранённые неактуальные события остаются видимыми серым. Неизвестный формат актуальности не считается подтверждённой неактуальностью. Текст, цвет, актуальность, сроки, версии и история SQLite не меняются; правило общее для обычных заказов, поставщиков и PNG. Свободные события и планы счетов/оплат сохраняют прежнее поведение.

Если строку снятой недели в календаре удерживает актуальное дневное событие, её сохранённый недельный комментарий виден серым (`#d1d5d8`, фон `#fafafa`). При возвращении отметки восстанавливается прежняя палитра, кроме самостоятельной неактуальности события. Это вычисляемое оформление по `deadline_weeks`, без записи флага актуальности, смены цвета или текста в базе; общее для обычных заказов, поставщиков и PNG. При обновлении существующих строк учитывается изменение сроков, узлы, фокус и прокрутка сохраняются. Дневные события используют прежние собственные цвета и актуальность.

По уточнению пользователя от 26 октября снятие отметки недели сохраняет её непустой комментарий в карточке; номер и поле сразу становятся серыми, поле остаётся редактируемым и после повторного открытия. Повторный выбор возвращает обычное оформление и показ в календаре. Недельный комментарий снятой недели сам по себе не добавляет строку заказа и не расширяет диапазон календаря; строка появляется по выбранному сроку или самостоятельному актуальному дневному событию. Если строку удерживает актуальное дневное событие, недельное поле остаётся доступным. Это общее правило обычных заказов и поставщиков, включая PNG; свободные события и планы оплат сохраняют прежнее поведение. Пустые строки снятых недель без несохранённого ввода, ошибки или сохранения убираются после ухода фокуса без перезагрузки. SQLite, текст, цвет и актуальность сохранённых событий не меняются; новых полей и миграций нет.

Диапазон календаря вычисляется в браузере из всех `deadline_weeks`, актуальных дневных событий обычных заказов и поставщиков, свободных дневных/недельных событий и планов счетов/оплат ответа SQLite. Границы — полные недели от самой ранней до самой поздней записи с обязательным включением текущей и следующей недель по Москве. Пустые промежуточные недели сохраняются. Фиксированного окна по месяцам нет; снятие отметки сужает диапазон, только если на неделе нет других источников. Неизвестные блоки не заменяются; неактивные ветки и незарегистрированные заказы исключены прежними правилами. Схема и рабочие данные не меняются. При изменении границ сохраняются узлы оставшихся недель, видимая дата, смещение, фокус и внутренняя прокрутка.

В колонке «Сроки» правее комментария — 16 маленьких кнопок в один ряд: текущая неделя и ещё 15, без переноса на узком экране. Нумерация ISO, неделя с понедельника по воскресенье; текущий день определяется сервером по Москве. На кнопке только номер, в подсказке полные даты начала и конца с годом. Можно отметить несколько недель, повторным кликом снять одну. Сразу справа от кнопок в той же строке показан диапазон `дд.мм-дд.мм`, без года: понедельник самой ранней и воскресенье самой поздней выбранной недели. Учитываются и сохранённые недели вне текущего окна; разрывы между выбранными неделями не разбивают общий диапазон. Без выбора или при неизвестном формате диапазон скрыт. Он вычисляется из сохранённых дат и отдельно не хранится. Это общий компонент главной и объекта.

В `orders.extra_blocks["Сроки"]` хранится JSON `{"version":1,"weeks":["2026-10-19","2026-10-26"]}`: уникальные отсортированные даты понедельников. Отсутствие блока означает пустой выбор; очистка сохраняется явно. Номера и положения кнопок не сохраняются, поэтому смена недели и ISO-года не перепривязывает отметки. Перед текущей дополнительно показан общий для всей таблицы набор прошедших недель, выбранных хотя бы у одного заказа исходного списка до поиска и фильтров. Даты идут по порядку, количество и положение кнопок одинаковые во всех строках и статусных группах: выбранная прошедшая неделя красная, невыбранная светло-серая. Одинаковые номера стоят строго друг под другом, легенда месяцев учитывает общий набор. Просрочка — дата понедельника раньше текущей недели по Москве, независимо от номера недели и ISO-года. Подсказка содержит «Просрочено», полные даты и комментарий. Эти отметки не исчезают при смене недели, опросе или обновлении страницы: пользователь сам снимает каждую одним кликом при перепланировании. Снятие делает кнопку светло-серой, пока эта неделя выбрана у другого заказа исходного списка; после снятия последней отметки она исчезает одновременно из всех строк таблицы. Комментарий сохраняется. Далёкие будущие даты за пределами 16 недель не удаляются: под кнопками показан их счётчик, в подсказке — даты начала. Неизвестная версия, дополнительные поля и некорректные прежние данные сохраняются без замены, кнопки отключаются.

Диапазон показан обычным шрифтом. Кнопки текущей и будущих недель окрашены постоянной палитрой календарных месяцев: месяц определяется по четвергу, то есть по большинству дней недели, в том числе на стыке года. Невыбранные бледные, выбранные насыщенные; текущая неделя дополнительно обведена. В каждой непустой шапке статусной группы, в колонке сроков, показана мелкая легенда месяцев. В строках заказов легенды нет, высота строк не меняется. Цвета и легенда вычисляются из дат, в SQLite не записываются.

В обычной зарегистрированной карточке — отдельный блок «Сроки» с тем же компонентом маленьких номерных кнопок и диапазоном справа. Показаны текущие шестнадцать недель, все сохранённые отметки, включая прошедшие и далёкие, и их соседи. Полные даты с годом — в подсказке, легенда при нескольких годах включает год. Разрыв между далёкими отрезками показан многоточием. Один клик ставит или снимает отметку; снятая неделя остаётся на экране для обратного клика. Локальный набор видимых недель живёт только до закрытия карточки, «Раньше»/«Позже» раскрывают по десять недель без изменения данных. Поля даты и отдельной кнопки добавления нет. В таблице 16 недель планирования и общий набор прошедших недель; выбранные недели карточки не обрезаются. Выбранная прошедшая неделя в карточке также красная, снятая становится светло-серой. Блок также доступен под карточкой зарегистрированного заказа поставщику в `# work`; скрыт у клиентов, объектов, событий, незарегистрированных папок и прямых заказов корня производства без поставщика.

Изменение сроков в карточке использует ту же `/api/order-deadline-week`, ждёт уже начатое сохранение карточки и передаёт актуальную после него версию. Обычное сохранение ждёт частичную запись. Несохранённые поля редактора и задачи не перерисовываются и не заменяются; последующее сохранение использует новую версию. Конфликт не переносит версию другого окна на локальный ввод, блокирует дальнейшие изменения сроков до открытия/обновления карточки и показывает причину. Неизвестный формат доступен только для чтения.

`/api/order-deadline-week` меняет одну отметку, версию и техническое состояние синхронизации. Отметки недель и комментарии к ним сохраняют прежнее `orders.updated`, чтобы не переставлять заказ при сортировке по обновлению. Порядок строк главной и объекта остаётся прежним после каждого клика, фонового опроса, повторного открытия и обновления страницы. Версия и история по-прежнему фиксируют все изменения; обычное сохранение карточки меняет время по прежним правилам. Обязательны путь, UUID заказа и версия показанной строки. История записывается в `metadata_history` той же транзакцией; статусы, финансы, заметка, задачи, закупки, избранное и остальные блоки не заменяются. Ошибки и конфликты не применяют локальный выбор. Чтение и сохранение работают без iCloud, файлы карточек не создаются. Обычное сохранение карточки, перенос/откат путей, снятие регистрации и повторное добавление сохраняют блок сроков.

Текст недели в карточке и подпись под кнопками в списке — недельное событие заказа, единый `orders.extra_blocks["События календаря на неделю"]`, JSON `{"version":1,"events":{"2026-10-19":"Проверить размеры"}}`. `calendar_week_events` используется во всех трёх местах. Отдельный блок «Комментарии к срокам» отменён. Ключ — реальная дата понедельника, значение — непустая строка до 1000 символов; максимум 5200 недель. Снятие отметки срока не удаляет событие; очистка поля в карточке удаляет это недельное событие, его цвет и отметку неактуальности, оставляя поле пустым; перенос меняет дату во всех представлениях. Неизвестный формат сохраняется без замены и отключает редакторы события, не мешая отметкам сроков.

В карточке плашка сроков находится под карточкой заказа в левой половине страницы: слева прежние кнопки, справа строки выбранных недель и всех сохранённых комментариев. Номер справа — неинтерактивный значок того же размера. После снятия отметки номер и поле сразу становятся серыми; непустой комментарий остаётся редактируемым и после повторного открытия. Пустая строка без несохранённого ввода и ошибок убирается после ухода фокуса. Кнопки сроков слева в карточке также включают недели сохранённых комментариев и соседей. На узком экране поля располагаются ниже кнопок.

Карточка использует `/api/order-deadline-comment` с `week` и `comment`: непустой текст меняет то же недельное событие, пустой удаляет только его текст, цвет и отметку неактуальности. Уже пустое поле сохраняется без ошибки. `/api/order-calendar-event` с `period: "week"`, `date` и `text` обслуживает календарь; пустой текст этого API по-прежнему означает неактуальность. Поле `deadline_comments` в ответе — вычисляемый алиас `calendar_week_events` для прежних вкладок, в SQLite отдельно не сохраняется. Операция меняет только одно недельное событие с обязательными путём, UUID и версией, повышением версии и историей той же транзакцией. Чтение и запись только SQLite, без iCloud или новых служебных файлов; отметки, остальные поля и неизвестные блоки сохраняются. Перенос/откат, снятие регистрации и повторное добавление сохраняют комментарии. Автосохранение через 700 мс после ввода, при выходе из поля и Enter; переход внутри приложения, смена отметки/звезды и обычное сохранение дожидаются записи. Одновременные записи сериализованы, новый ввод во время запроса сохраняется следующей версией. Узлы полей сохраняются для фокуса и позиции ввода; IME и несохранённые поля карточки не заменяются. Ошибка оставляет текст и повтор, конфликт блокирует правки сроков без переноса чужой версии на локальный ввод. Закрытие вкладки с несохранённым текстом предупреждает. В общей таблице главной и объекта подсказка каждой кнопки включает даты и сохранённый комментарий, даже после снятия отметки.

## Перенос комментариев недель в события

`weekly_events_migration.py --database … --apply` выполняется на M4 после развёртывания совместимого кода. Без `--apply` только проверяет план. В SQLite берётся `BEGIN IMMEDIATE`, который удерживает запись на время проверки, снимка и единой транзакции. План охватывает все `orders`, включая снятые регистрации, и `folder_notes.document.extra_blocks`. Известные прежние комментарии переносятся в недельный календарный блок; точные одинаковые тексты одной даты не дублируются, пустые/пробельные записи не создают события. Разные непустые тексты одной даты, неизвестный формат или блокировка пути останавливают весь перенос. Ни одна строка до проверки всего плана не меняется.

В новом уникальном каталоге `data/backups/weekly-events-…` сохраняются согласованный `before.sqlite3`, проверенный `integrity_check`, числом строк всех таблиц и SHA-256, `plan.json` с точными полями до/после, результат и самостоятельный `.restore.py`. Прежний ключ удаляется, версии затронутых записей повышаются на один, снимки вычисляемого `deadline_comments` в черновиках убираются. Старые значения сохраняются в `metadata_history` той же транзакцией. UUID, пути, регистрация, `updated`, сроки, дневные/свободные события, финансы и прочие поля сохраняются. Повторный запуск при отсутствии прежних блоков не меняет версии. Исходные документы и вложения не читаются и не меняются.

Импорт известных прежних блоков сразу нормализует их к недельному событию; неизвестные оставляет без замены. Чтение старого блока поддерживается только как совместимость до переноса, новых записей в него нет. `metadata_settings.weekly_events_unified=1` отмечает новый контракт. Откат/деплой старого кода без `WEEKLY_EVENTS_UNIFIED_VERSION = 1` блокируется. `.restore.py` возвращает только нетронутые после переноса поля с новой версией и историей, целиком останавливается при конфликте и не снимает защиту архитектуры; рабочую базу, новые записи и остальные поля он не заменяет.

## Сроки поставщиков в календаре

Подпись первой колонки строится из прежних полей как «work_supplier · title» (при отсутствии названия — прежний path), с тем же порядком в aria-label и PNG. Перед ней остаются включённые отметки. Это только порядок прежних элементов ссылки, без изменения данных, запросов, цветов или размера строки; обычные заказы сохраняют «название · клиент».

Дневные и недельные события поставщиков используют нежирный текст (`font-weight: 400`) фиксированного цвета поставщика без собственной фоновой заливки, включая PNG. Серый текст неактуальных, выполненных и комментариев снятых недель, а также галочка выполнения сохраняются, тоже без заливки. Это только CSS-оформление: цвета поставщиков, тексты, отметки, версии, история и формат SQLite не меняются.

Зарегистрированные заказы внутри разделов поставщиков `# work` определяются непустым вычисляемым полем `work_supplier`. Их карточка показывает тот же блок сроков и комментариев под редактором названия и заметки. Блоки SQLite, частичные операции, обязательные версии и история, защита несохранённого ввода и сохранение `updated` общие с обычными заказами; нового хранения нет. Прямые заказы корня производства без поставщика этим правилом не затронуты.

`/api/orders` отдаёт их отдельным массивом `calendar_supplier_orders` после общих проверок неактивности, из SQLite без чтения документов. `orders` остаётся без всей ветки производства; общие таблицы, поиск, фильтры, счётчики, финансовые итоги и сводки To-do используют прежний источник. Избранное сохраняет прежний состав. Календарь объединяет обычные заказы с этим массивом, отбирает недели по выбранным срокам и дневным событиям, показывает фактического поставщика рядом с названием. Дневные и недельные события, правка и перенос используют прежние операции и версии заказа; опрос и локальные записи обновляют отдельный массив без потери фокуса/прокрутки. Снятие регистрации скрывает заказ и в календаре, сохраняя все сроки и события для возврата.

План выписки счёта в дневной и недельной шапке календаря отображать обычной строкой колонки поступлений. Вместо суммы — зелёный плюс и четыре буквальных звёздочки `+ ****`, рядом серым только название заказа. Каждая строка ведёт в свой заказ, со стандартной новой вкладкой и прежней подробной подсказкой; название обрезается многоточием при нехватке места. Отдельной колонки и синих галочек выписки нет. Несколько планов остаются отдельными строками. Это только оформление operation=invoice: звёздочки не сумма, данные плана и фактические финансы сохраняются. Неактуальность, строки оплат, кнопки над датой, рост шапки, фокус и прокрутка работают по прежним правилам.

## Удаление записей календаря

Удаление из календаря: текстовые события заказов, поставщиков и свободные записи удаляются только на день. В календаре недельные текстовые события не удаляются, сервер проверяет фактический период; очистка комментария недели в карточке заказа — отдельное разрешённое действие. Поступления и затраты без заказа можно удалить и на день, и на неделю; планы с заказом из календаря не удаляются. «Удалить» доступно в контекстном меню и редакторе существующей разрешённой записи. В уведомлении есть «Отменить». У дневного события заказа удаляется выбранная дата и её флаг актуальности; сроки, недельные события, остальные поля и updated сохраняются. У свободного события выставляется calendar_events.deleted=1 с сохранением текста и цвета, у оплаты используется прежняя корзина invoices без файловых действий. Удаление и отмена требуют UUID, текущую версию и путь заказа; история сохраняется той же транзакцией. Неизвестные форматы не заменять; устаревшее создание не возвращает удалённую запись. Отмена возвращает текст и актуальность, не перезаписывает занятую дату и проверяет версию. Опрос, прокрутка, фокус и ввод при ошибке сохраняются.

POST /api/order-calendar-event-remove и /api/order-calendar-event-restore меняют дневную запись заказа; /api/calendar-event-remove и /api/calendar-event-restore — свободное дневное событие; /api/calendar-payment-remove и /api/calendar-payment-restore — поступление/затрату без заказа любого периода. Период и привязка проверяются по текущей записи SQLite. У заказа отмена передаёт исходный text и is_inactive, использует версию после удаления и не заменяет занятую дату.

## Неактуальные события календаря

Контекстное меню каждого события содержит «Неактуально» с `aria-checked`; повторный клик снимает отметку. Это касается дневных и недельных записей обычных заказов и поставщиков, свободных событий, планов выписки счёта, получения оплаты и платежа. Текст и дата остаются видимыми, цвет текста `#d1d5d8`, фон `#fafafa`, при наведении `#c7cdd1`/`#f4f6f7`; прежний цвет сохраняется и возвращается при снятии отметки. Кнопки удаления в календарном диалоге нет. Пустой текст `/api/order-calendar-event` сохраняет прежний текст и помечает его неактуальным. Очистка недельного поля карточки через `/api/order-deadline-comment` удаляет запись вместе с её цветом и флагом неактуальности, без изменения сроков и остальных дат. Исторические свободные записи с `deleted=1` остаются скрытыми; новые удаления не создаются.

У заказа отдельный блок `orders.extra_blocks["Неактуальные события календаря"]`: `{"version":1,"day":["2026-10-26"],"week":["2026-10-26"]}`. Списки отсортированы, без повторов, не более 5200 дат каждый, у недель — понедельник. Отсутствующий блок означает пустые списки. `calendar_inactive` — вычисляемое поле ответа, неизвестный формат возвращает `null`. `POST /api/order-calendar-inactive` требует путь, UUID, версию, дату, период и булево `is_inactive`; существование события, формат и версия проверяются в той же транзакции, что флаг и `metadata_history`. Дневная и недельная отметки независимы. Перенос текста атомарно переносит и его флаг. Редактирование, снятие срока, перенос папки и снятие/возврат регистрации сохраняют отметку; `updated`, остальные данные и фактические финансы заказа не меняются.

У свободного события колонка `calendar_events.is_inactive INTEGER NOT NULL DEFAULT 0`; прежние записи остаются актуальными. При добавлении колонки триггеры аудита пересоздаются, чтобы история сохраняла флаг. `POST /api/calendar-inactive` меняет его с UUID, версией и булевым значением, сохраняя текст, дату, период, цвет и `deleted`. У плана `invoices.data._calendar_inactive` с булевым значением; `POST /api/invoice-plan-calendar-inactive` требует путь, UUID, версию и состояние, проверяет зарегистрированного владельца, тип плана, корзину и формат. Сохраняет `invoice_history`, вид операции, дату, сумму и прочие поля; без PDF, номера, очереди и изменений фактической оплаты. Поле ответа календаря содержит версию и `is_inactive`. Неизвестные состояния не заменяются.

Фоновый опрос сохраняет фокус и прокрутку, открытый редактор — свой ввод и версию; конфликт требует обновления перед повторным выбором. Перемещение, редактирование и смена цвета сохраняют неактуальность. Маркер SQLite `metadata_settings.calendar_event_relevance=1` блокирует деплой/откат к коду без `CALENDAR_RELEVANCE_VERSION = 1`, чтобы прежняя версия не скрыла отметки и не вернула удаление событий.

## Свободные события календаря

События без заказа хранятся в отдельной таблице `calendar_events` рабочей SQLite: `id` (UUID), `version=1`, `period` (`day`/`week`), точная `date` (для недели — понедельник), однострочный непустой `text` до 1000 символов, `color`, `revision`, `created`, `updated`, `deleted`. На одну дату допустимо несколько независимых событий. Папок, файлов и записей заказов они не создают. Резервные копии SQLite включают таблицу обычным порядком; перемещения папок и регистрация заказов к ней не относятся.

`/api/orders.calendar_events` возвращает активные записи из SQLite без iCloud; `GET /api/calendar-event?id=…` читает одну запись, в том числе помеченную удалённой. `POST /api/calendar-event` создаёт UUID с `revision:0` или меняет текст существующего с обязательной версией и прежними датой/периодом. Повтор неизменённого запроса создания идемпотентен, повтор UUID с иным содержимым запрещён. Пустой текст прежнего API помечает существующее событие неактуальным с сохранением текста, UUID и `deleted=0`; прежние удалённые записи сами не восстанавливаются. `POST /api/calendar-move` атомарно меняет дату: дневное событие ±1 или ±7 дней, недельное — только ±7. Занятая дата допустима, другие события сохраняются. `POST /api/calendar-color` меняет только цвет, версию и время правки; допустимы `gray`, `red`, `orange`, `yellow`, `green`, `blue`, `purple`, по умолчанию `gray`. Все правки проверяют версию UUID и сохраняют прежнее состояние в `metadata_history` той же транзакцией. Неизвестный формат или цвет сохраняется без замены и отключает правки.

В каждой неделе свободная область идёт ниже строк заказов: недельные события в колонке «На неделю», дневные в своей дате. События компактные, высотой 12 пикселей; список прокручивается вместе с заказами. Кнопка «+» и пустое место под событиями открывают новую запись. По правому клику или Shift+F10 открывается прежнее меню переноса и ряд из семи цветных кружков; выбранный отмечен белой точкой. Кружки доступны с клавиатуры и подписаны через `aria-label`, всплывающих подсказок нет. Смена цвета сохраняется после опроса, редактирования, переноса и перезапуска. Диалог общий с событиями заказов: ввод и версия независимы от опроса, конфликт оставляет текст и требует явной проверки изменений. Удалённое или перенесённое в другом окне событие не пересоздаётся из старой формы. Прокрутка, фокус, три видимые недели и размеры строк заказов сохраняются.

## События календаря заказов

Дневные и недельные события обычных заказов имеют ту же палитру из семи цветов, что свободные события: красный, оранжевый, жёлтый, зелёный, синий, фиолетовый, серый. Правый клик или Shift+F10 открывает цветные кружки с белой точкой выбранного цвета. Без явного выбора прежнее оформление сохраняется. Цвет относится к конкретному событию, независимо от остальных дат и периода; правка текста, отметка «Неактуально», перенос, опрос и перезапуск его сохраняют. Неактуальное событие приглушается, снятие отметки возвращает выбранный цвет. У поставщиков палитры нет: дневные и недельные события всегда используют фиксированный цвет поставщика, сервер отклоняет смену цвета.

Цвета событий заказов хранятся только в SQLite в orders.extra_blocks["Цвета событий календаря"]: JSON version=1 с day и week — словарями дата → цвет; недельные ключи — понедельники. Отсутствующий блок означает отсутствие ручного выбора. Поле ответа calendar_colors, неизвестный формат — null без замены исходных данных; правка текста остаётся доступной, смена цвета, перенос и удаление отключаются сервером. POST /api/order-calendar-color меняет только цвет выбранного существующего события с обязательными путём, UUID, revision и периодом (по умолчанию day), одной версией и историей; updated и остальные данные не меняются. Перенос атомарно переносит цвет вместе с событием и актуальностью. Удаление дневной записи убирает её цвет; «Отменить» возвращает прежний цвет, новая запись не наследует удалённый. Маркер metadata_settings.order_calendar_colors=1 блокирует код без ORDER_CALENDAR_COLORS_VERSION = 1 при деплое и откате. Новых файлов, папок и таблиц для цветов нет.

Одна текстовая запись на заказ и дату хранится в `orders.extra_blocks["События календаря"]`: JSON версии 1 с `events` — словарём реальных дат `ГГГГ-ММ-ДД` и непустых текстов до 1000 символов без переноса; не более 5200 дат. Пустой текст прежней операции помечает существующую запись неактуальной без удаления; новую пустую запись не создаёт. Неизвестный формат возвращает `calendar_events: null`, редактор отключён, исходный блок сохраняется.

Частичная операция `/api/order-calendar-event` требует путь, UUID заказа, целочисленную версию, дату и текст. Проверка регистрации, блокировки пути и идентичности, обновление одной даты, повышение `revision` и `metadata_history` происходят в одной транзакции. `updated`, сроки, комментарии к ним, статусы, финансы, To-do, закупки, избранное и неизвестные блоки не меняются. Сохранение и чтение только SQLite, без iCloud и новых файлов/папок. Перенос, откат, снятие регистрации и возврат сохраняют блок вместе с заказом.

Календарь показывает заказ в неделе, если она отмечена в сроках или содержит событие; снятие срока не удаляет и не скрывает события. Все семь дней и заказ лежат в одной компактной строке с общей подсветкой и прокруткой внудве недели. Открытый диалог хранит свою версию и ввод независимо от опроса. Конфликт не перезаписывает чужую запись: текст остаётся в поле, явная проверка изменений показывает актуальную запись, повторное сохранение требует отдельного нажатия. Всплывающих подсказок у обычных событий нет; отдельные планы счетов и оплат в шапке дня имеют подсказки. Полные названия и даты доступны в диалоге и через `aria-label`.

Сдвиг события выполняет `/api/order-calendar-move`: обязательны путь, UUID заказа, целочисленная версия, исходная дата и целочисленное `days` строго из `-7, -1, 1, 7`. В одной транзакции после проверки регистрации, блокировки пути и версии точный текст убирается с исходной даты и добавляется на целевую, `revision` повышается один раз с историей. Занятая дата не перезаписывается, даже если тексты совпадают; отсутствующий источник, неизвестный формат, некорректная дата/сдвиг или конфликт оставляют весь блок без изменений. При переносе в другую неделю её понедельник добавляется в `orders.extra_blocks["Сроки"]` (`deadline_weeks`) той же транзакцией: это правило для дневных и недельных событий обычных заказов и поставщиков. Уже выбранная неделя не дублируется; все прежние отметки сохраняются. Перенос внудве недели сроки не меняет. Неизвестный формат сроков или превышение их лимита отклоняет весь перенос без изменения события, актуальности, версии и истории. Другие события, `updated`, поля карточки и неизвестные блоки сохраняются. Даты вне текущего диапазона просмотра сохраняются без расширения самого диапазона; уведомление показывает новую дату, автоматической прокрутки нет.

### Недельные события

После названий заказов календаря — отдельная колонка «На неделю» с ISO-номером в каждой шапке недели. Одна недельная запись на заказ и дату понедельника хранится отдельно в `orders.extra_blocks["События календаря на неделю"]`: JSON версии 1 с `events`, ключи — реальные даты понедельников, значения — непустые тексты до 1000 символов без переноса; максимум 5200 записей. Поле ответа — `calendar_week_events`; неизвестный формат возвращает `null` только для этого периода, исходный блок сохраняется. Дневной и недельный блоки независимы, в том числе при совпадающей дате.

Операции `/api/order-calendar-event` и `/api/order-calendar-move` принимают `period: "week"` для недельных записей, `period: "day"` или отсутствие поля — для прежних дневных. Иной период отклоняется. Для недельного события обязательна дата понедельника; перенос — только `days` ±7, занятая неделя не перезаписывается. Путь, UUID, обязательная версия, транзакционная история, независимость остальных данных и `updated` — как у дневных событий. Снятие срока, регистрации, перенос папки и откат сохраняют оба блока; календарь включает недели с записями любого периода. Общая строка охватывает девять равных колонок, прокрутка и подсветка синхронны, высота двух недель прежняя.

Под кнопками недель общей таблицы главной и объекта показана одна строка комментариев: `47-комментарий, 48-комментарий`, по дате понедельника. Включать все непустые сохранённые комментарии, в том числе снятых и вышедших за окно недель; текст не менять. Шрифт 10 пикселей с высотой строки 12 пикселей и отступом 4 пикселя от кнопок, без полужирного, приглушённый. Подпись занимает только ширину кнопок, не диапазона справа; длинный текст сокращён многоточием без переноса. Она располагается в свободном месте под кнопками внутри существующей ячейки и не увеличивает высоту строки или ширину таблицы. Полный текст с датами и годом — при наведении. Если есть счётчик «Вне окна» или неизвестный формат сроков, он показан первым в этой же строке. В карточке остаются собственные поля комментариев, без дублирования мелкой подписью. Чтение только из уже загруженного `deadline_comments`, без запросов, изменений SQLite или влияния на сортировку.

Travel-календарь пока задан вручную: ISO-недели 51–53 2026 года и 1–4 2027 года, с 14 декабря 2026 по 31 января 2027 включительно. Над соответствующими кнопками сроков проходит тонкая жёлтая линия независимо от выбора недели; при наведении дополнительно видно «Travel · Таиланд». Линия общая для главной, объекта и карточки, не увеличивает высоту строк и не меняет цвет месяца или просрочки. Период привязан к конкретным датам, не повторяется ежегодно. Отдельного редактора и записей SQLite пока нет; сроки, комментарии, сортировка и события календаря не меняются.

## Сворачивание групп заказов

Каждая непустая статусная группа общей таблицы главной и объекта имеет кнопку со стрелкой и числом заказов. Повторный клик разворачивает строки; Enter и пробел работают так же. Скрытие строк не меняет поиск, фильтры, итоги, сортировку, календарь или данные заказов. Шапка и легенда месяцев остаются видимыми. Впервые все группы развёрнуты; скрытая фильтром пустая группа сохраняет свой прежний выбор.

Это локальное предпочтение вида, не рабочая информация заказа: `localStorage` текущего браузера, ключ `zigzag.order-groups.v1:` + JSON-массив `[scope, group]`, значения `1` (свёрнуто) и `0` (развёрнуто). `scope` — `main` либо `object:` с полным NFC-путём объекта; группы имеют постоянные ключи `preparation`, `production`, `other`, `hidden`. Главная и каждый объект независимы. Выбор восстанавливается при обновлении страницы, новом открытии браузера, переходах и фоновых обновлениях; с другими браузерами и устройствами не синхронизируется. SQLite, документы и версии карточек не меняются, iCloud не читается. Если браузер запретил запись, текущий вид работает в памяти, а уведомление сообщает, что после обновления он может сброситься. Переключение меняет только видимость строк, фокус кнопки сохраняется при опросе.

## Избранные заказы

Зелёный доллар — независимая ручная отметка в списках заказов, колонка между синим плюсом и флажком. Хранится в `orders.extra_blocks["Зелёный доллар"]` как «Да»/«Нет»; отсутствие означает false, неизвестный формат — null без замены данных. Поле ответа `is_dollar` читается в обычных списках, производстве и черновиках объекта. `/api/order-dollar` принимает путь, UUID, целую revision и строгий boolean `is_dollar`, частично меняет только блок и revision с историей той же транзакцией, сохраняя updated. Сохранение карточки, снятие/возврат регистрации, перенос и откат сохраняют отметку. Не влияет на статусы, финансы, счета, сортировку, поиск, группы, задачи или сроки; схема и документы не меняются.

Календарь показывает включённые синий плюс, зелёный доллар, флажок и звёздочку перед названием обычного заказа или заказа поставщика. Источник — уже загруженные поля `is_blue_plus`, `is_dollar`, `is_flagged`, `is_favorite` ответа SQLite `/api/orders`; только строгое `true` включает значок. Выключенные, отсутствующие и неизвестные значения скрыты. Отдельных запросов, записей и изменений формата хранения нет; индикаторы входят в ту же ссылку заказа и её `aria-label`, а также в PNG календаря. Опрос обновляет отметки без потери фокуса и прокрутки.

Слева от звёздочки в общей таблице главной и объекта — отдельный ручной флажок. Хранится как `orders.extra_blocks["Флажок"]`: «Да»/«Нет», без блока выключен. В ответах SQLite поле `is_flagged`; неизвестный текст сохранён без замены, кнопка отключена. Один клик ставит, повторный снимает. Это только визуальная отметка: сортировка, группировка, поиск, фильтры, итоги, статусы, избранное, сроки и задачи её не используют.

Частичная `/api/order-flag` требует путь, UUID и версию показанной строки, меняет только блок и версию, фиксирует историю той же транзакцией. `updated` сохраняется, поэтому порядок по дате обновления не меняется. Чтение/запись только SQLite без iCloud и служебных файлов. Обычное сохранение карточки, снятие/возврат регистрации, перенос и откат сохраняют флажок. У папок без регистрации кнопка недоступна. В общей разметке это узкая колонка перед звёздочкой; активный значок приглушённо-красный, неактивный серый, высота строк прежняя. Конфликт перечитывает список и требует повторного клика; фокус и прокрутка сохраняются.

В самой левой узкой колонке общей таблицы главной и объекта — независимый синий плюс: один клик ставит отметку, повторный снимает; выключенный бледно-синий, включённый жирный тёмно-синий на лёгком голубом фоне. Далее идут зелёный доллар, красный флажок и звёздочка. Синий плюс — только ручной маркер, без влияния на сортировку, группировку, поиск, фильтры, избранное, флажок, статусы, финансы, задачи и сроки. Хранить в SQLite `orders.extra_blocks["Синий плюс"]` как «Да»/«Нет»; отсутствие означает выключенный, ответ `is_blue_plus`. Частичная `/api/order-blue-plus` требует путь, UUID, логическое состояние и обязательную версию, меняет только этот блок с повышением версии и историей той же транзакцией; `updated` сохраняется. Неизвестный формат сохранять и отключать кнопку. Карточка, снятие/возврат регистрации, переносы и откат сохраняют отметку. У незарегистрированных папок кнопка недоступна. Фоновое обновление сохраняет фокус и прокрутку; iCloud не читать, служебные файлы не создавать.

Отметка `[Избранное]` с `Да`/`Нет` хранится среди дополнительных блоков SQLite. Отсутствие означает выключенную звёздочку, неизвестный текст сохраняется без замены. Смена проверяет версию и меняет только отметку. Таблица разделена на части: `new`/`measure`/`process`/`awaiting_payment`, затем `workshop`/`install`/`rework`/`finishing`, затем `waiting` («Жду»), `offer_later` («Предложить позже»), `deferred` («Отложен/возможно») и остальные статусы. Это представление данных без дополнительных записей SQLite; пустые части скрыты. Внутри каждой статусной части при любой сортировке сохраняются группы клиентов и объектов; избранные выше внутри своего объекта, затем действует выбранный столбец и направление. Заголовки клиента и объекта меняют направление соответствующего уровня группировки. Ненажатая звёздочка приглушена. Поиск, фильтры и неактивность сохраняют действие.

Колонка «Объект» расположена сразу после клиента в общей таблице главной и объекта. `folder_structure.order_location` вычисляет поля ответа `client_path`, `object`, `object_path` только из сохранённого пути: с учётом клиента в числовой группе, без годов и числовых контейнеров в названии объекта. Вложенные имена соединены через « / »; если объекта нет, показан прочерк в конце клиента. Идентичность групп — полный путь в NFC: одинаковые подписи разных путей не объединяются. Для прежних заказов непосредственно в корневой числовой группе ключом клиента остаётся эта группа. Поля вычисляемые, рабочие строки SQLite, UUID, версии и история от показа не меняются; чтение iCloud не требуется. Поиск включает название объекта. По умолчанию клиенты и объекты по алфавиту с естественными номерами, пустые значения в конце; выбранный столбец сортирует заказы внутри объекта после избранного.

Названия клиента и объекта в общей таблице — обычные ссылки на `client_path` и `object_path`, при обычном клике используется переход приложения с сохранением текущего ввода. Открытие в новой вкладке доступно стандартными средствами браузера. Без пути показывается только текст/прочерк. Ссылки вычисляемые и не меняют записи SQLite.

## Формирование закупок/затрат

Это отдельные задачи с текстом, выполнением и переключателями `newtek`, `glass`, `antares`, `tbm`, `remex`. Состояния кнопок сохраняются в SQLite, неизвестное старое содержимое сохраняется без замены. Пока кнопки не создают заказы в `# work`. На главной после To-do есть кнопка со счётчиком актуальных закупок и окном; в заказе блок расположен в правой колонке сразу под To-do, независимо от высоты левых блоков. Поставщики идут в строку с переносом при нехватке места.

## Избранные разделы производства

Звезда раздела `#…` в корне `# work` хранится в `metadata_records`, вид `work_supplier_favorite`, с UUID и версией. JSON содержит `version: 1`, `is_favorite` и `position`. При первом открытии существующие antares, himlex, newtek, glass отмечаются в этом порядке; запись `work_supplier_favorite_defaults` по пути корня делает начальную настройку однократной. Позднее появившиеся разделы без звезды, включая прежние имена поставщиков, отсутствовавшие при настройке. Отмеченные позже получают следующее место; снятие и повторное включение сохраняют прежнее место.

Сохранение требует текущую версию, меняет только эту запись и фиксируется в истории той же транзакции. Неизвестный формат сохраняется, звезда доступна только для чтения. Привязка следует общему переносу путей и откату. Чтение между окнами каждые 5 секунд и сохранение звезды используют только SQLite без доступа к папкам iCloud; старый ответ не заменяет новую версию, ввод заметки, фокус и прокрутка остаются. Карточки, обычное избранное заказов, цвета и пути не меняются. Папки без `#` не участвуют в этой отметке.

## Цвета поставщиков

Цвет раздела `# work` закреплён за его путём в `metadata_records` вида `work_supplier_color`. Значение содержит `version: 1`, маркер `palette: 2`, оттенок `hue` и признак светло-серого оформления `neutral`. Палитра 2: antares — красный (0°), cutter — фиолетовый (270°), freza — бирюзовый (180°), glass — оранжевый (30°), himlex — золотистый (55°), laser — синий (215°), newtek — зелёный (125°), print — розовый (325°), razbor — светло-серый. Новым поставщикам выбирается максимально свободный оттенок, не меняющий существующие привязки.

После согласованной замены близких оттенков прежние записи без маркера палитры обновляются один раз: UUID и дополнительные поля сохраняются, версия повышается, прежнее значение остаётся в истории. Перед запуском обработчиков создаётся проверенный снимок `before-supplier-palette-v2`. Формат `version: 1` остаётся читаемым прежним кодом. Последующие чтения сохраняют UUID, версию и время записи; неизвестный формат или версия палитры не перезаписываются.

Кнопка раздела, заголовок заказа и заголовок события используют одно значение базы. Чтение не обращается к iCloud и не меняет карточку заказа. Привязка следует общему переносу путей SQLite и самостоятельному откату с повышением версии и историей в той же транзакции; исходные файлы не меняются.

## Подборки производственных заказов

Во всей ветке `# work` интерфейс скрывает «Формирование закупок/затрат» и «Счета», не загружает список счетов фоном. Прежние строки закупок, поставщики, записи счетов и PDF сохраняются в текущем хранилище. При сохранении производственной карточки поле `purchase_items` не отправляется: скрытые значения остаются в SQLite без очистки или перезаписи. Обычные заказы вне производства используют прежние редакторы и очереди.

Производственные заказы корневой ветки `# work` остаются в общей SQLite, но не входят в `orders` ответа `/api/orders`: главный список, поиск, счётчики и финансы используют только обычные заказы. Отдельное поле `favorites` того же ответа включает избранное всех видимых зарегистрированных заказов, в том числе производства. Фильтрация использует путь из базы; файлы и регистрации не меняются.

Зарегистрированный заказ непосредственно в `# work` хранит выбранные UUID в блоке `Связанные заказы поставщиков` в `orders.extra_blocks`: JSON с `version: 1` и `order_ids`. Выбор ограничен 200 уникальными идентификаторами. Добавляются только зарегистрированные заказы производственных разделов и прежней корневой `# glass`; другие подборки, события, финансовые и клиентские заказы не добавляются. Уже сохранённые недоступные или снятые с регистрации связи остаются до явного удаления из подборки. Пустой список сохраняется явно; неизвестная версия/форма блока доступна без автоматической замены.

Операция меняет только этот блок с проверкой версии родительской карточки; история записывается тем же триггером в одной транзакции. Поля редактора, закупки, звезда, финансы, статусы и задачи не заменяются. Фоновое чтение использует SQLite, без проверки наличия папок в iCloud. Путь и название связанного заказа разрешаются по UUID при чтении: переименование и самостоятельный откат не требуют переписывать связи. Снятие регистрации сохраняет идентичность и подборку; повторная регистрация восстанавливает её. Каталоги и вложения не перемещаются, финансовые итоги и задачи автоматически не объединяются.

## Активность клиента и объекта

Неактивность — независимая отметка базы в карточке клиента или объекта. Скрывает их ветку дерева и заказы с задачами на главной, сохраняя данные. «Неактивные» возвращает ветки приглушёнными. Снятие отметки возвращает их в рабочий список. Неактивность объекта не меняет клиента и соседние объекты.

## Актуальность события и эскиза

Четыре состояния: «Без статуса», «Актуально», «Проверить», «Неактуально». Сохраняются среди дополнительных блоков `folder_notes`; у CDR — в записи непосредственной `#cdr`. Смена проверяет версию и меняет только соответствующий блок. Неизвестное содержимое не заменяется. Неактуальные плитки приглушены и доступны для открытия; актуальность не скрывает задачи на главной.

CDR-превью извлекаются из встроенного PNG, оригиналы открываются в CorelDRAW на M4. Бэкапы в плитки не входят. Имя отдельного файла автоматически не перепривязывается; перенос всей папки через менеджер меняет связанные пути базы.

## Комментарии к файлам

Каждый комментарий привязан к полному относительному пути NFC и независимой версии `UUID:число`. В запросах и ответах дополнительно проверяется ключ папки/имени. Положение в сетке и удаление соседнего файла не меняют привязку. Старые вкладки после переноса папки не могут записать комментарий по новому пути.

Поле справа в окне просмотра редактирует комментарий файла, слева показана заметка открытой папки только для чтения, включая текущий несохранённый ввод. Сохранение — кнопкой, ⌘S, закрытием или переключением файла; при ошибке окно остаётся с текстом. Подпись карточки обновляется только при совпадении пути и ключа. Оригиналы не меняются. Полный сохранённый комментарий используется в PDF-отчёте. Новые `.file-comments` не создаются.

## Закрывающие документы в строке счёта

Закрывающие документы прикрепляются непосредственно в строке конкретного счёта (черновик, issued или external), выбором нескольких файлов или перетаскиванием на строку; передача только по «Прикрепить». Любые непустые файлы до 20 МБ каждый, до 100 документов на счёт. В этой же строке — названия для открытия/скачивания, размер, удаление в свёрнутую корзину закрывающих и восстановление. SQLite хранит неизменяемые байты в invoice_documents: UUID документа, invoice_id, version=1, имя NFC, MIME, размер, SHA-256, content BLOB и время, а также filename/exported/sync_error устойчивой очереди копии. Версионируемый invoices.data._closing_documents содержит version=1 и items с метаданными и deleted; списки счетов читают только метаданные без BLOB документов. Загрузка, удаление и восстановление требуют путь, UUID счёта, UUID документа и текущую версию счёта; ссылка, версия и invoice_history сохраняются одной транзакцией. Повтор UUID с теми же байтами и счётом идемпотентен, не меняет поздние отметки и не возвращает удалённую связь; иной файл или счёт с тем же UUID запрещён. Каждый запрос файла проверяет связь, путь, UUID, корзину счёта, формат и SHA-256 через SQLite; PDF/PNG/JPEG открываются, прочие файлы скачиваются как application/octet-stream с nosniff. Файлы не исполняются и не перезаписываются. Копии закрывающих автоматически публикуются в # bills заказа через устойчивую очередь: сразу после загрузки, при запуске и с повтором через 15 секунд. Имя копии содержит UUID, чужой файл не перезаписывается; состояние и ошибки копии видны в строке. Источник — неизменяемый BLOB SQLite, исходный выбранный файл не меняется. Удаление связи убирает документ из строки, опубликованная копия в # bills сохраняется; восстановление связи возвращает доступ без повторной записи оригинала. UUID счёта сохраняет привязку при переименовании и корзине/восстановлении счёта; правка черновика и выпуск сохраняют закрывающие, новый «На основе» их не наследует. Неизвестный формат сохранять без замены. Опрос сохраняет выбранные File, фокус и раскрытую форму, конфликт требует «Проверить изменения» перед ручным повтором. Новая таблица входит в обычные снимки и ZIP SQLite; безвозвратного удаления нет. При наличии новых данных откат к коду без INVOICE_CLOSING_DOCUMENTS_VERSION = 1 или INVOICE_PAID_STATUS_VERSION = 1 блокируется.

POST /api/invoice-document-upload принимает один файл в Base64 с текущей revision; GET /api/invoice-document с path/id/document_id выдаёт исходные байты. POST /api/invoice-document-remove и /api/invoice-document-restore меняют только deleted в метаданных связи. В ответе счёта closing_documents, closing_documents_trash и closing_documents_editable.

## Перенос дат планов в календаре

`POST /api/invoice-plan-calendar-move` переносит существующий план поступления, затраты или выписки счёта с заказом и без него. Обязательны `path` (пустая строка для самостоятельной оплаты), UUID `id`, целая текущая `revision`, исходная `date`, `period` (`day` по умолчанию для прежних дневных записей) и целое `days` из `-7, -1, 1, 7`. Для сохранённого недельного плана разрешены только `-7, 7`; переданный период не подменяет фактический. Дата, период и версия сверяются с записью. Корзина, неизвестный формат плана, недопустимый сдвиг и выход за диапазон дат блокируют запись целиком; повтор с прежней версией не выполняет второй перенос.

В одной транзакции меняется только `invoices.data.date`, повышается версия плана, обновляется его техническое время и сохраняется прежний JSON в `invoice_history`. Сумма в копейках, направление, комментарий, связь с исходным счётом, актуальность и неизвестные дополнительные поля остаются прежними. Совпадение даты с другим планом допустимо; его данные и версия не меняются. Заказы, сроки, фактические финансы, PDF, нумерация и документы не затрагиваются. Новых таблиц, файлов и миграций нет.

## Выписка счетов

В списке «Счета» карточки заказа заголовок плана `operation=invoice` (также прежний план без operation) выделяется зелёной плашкой, фон `#e1f1e5`, текст `#2f7d46`. Правило общее для дневных и недельных планов. Дата, комментарий, ссылки, редактирование, корзина и опрос прежние. Это только HTML/CSS-оформление карточки; календарь, PNG и формат хранения SQLite не меняются, запись данных не выполняется.

### Оплаты по готовым счетам и без счёта

В карточке заказа связанные планы внутри строки счёта вычисляют приглушённое оформление по `source.list_status="inactive"` или собственной `data._calendar_inactive=true`: серый текст и подпись «Неактуально:» вместо «Запланировано:». Пометка входит в подсказку и доступное имя. Дата, сумма, направление и комментарий прежние, правка и корзина доступны; дневные, недельные, частичные, incoming/outgoing, issued/external используют одно правило. Снятие неактуальности источника возвращает прежнюю палитру только планам без собственной отметки. Это оформление по уже загруженным данным, без запросов, записи SQLite, изменения версий, истории и фактических финансов. Опрос и локальное переключение сохраняют прежнюю защиту ввода и фокуса.

Календарь исключает планы, связанные через `data.invoice_id` с `issued`/`external` того же `path`, если источник имеет `_list_status="inactive"`, `_list_status="paid"` или `_trash`. Проверка выполняется в чтении SQLite по точному UUID и пути, без загрузки PDF и сопоставления сумм/названий. Исключаются все частичные оплаты, дневные и недельные поступления/затраты. Данные плана не удаляются и связь не разрывается: его версия, история, сумма, дата, направление, комментарий и собственная актуальность сохраняются; в карточке план остаётся доступным. Снятие отметки «Оплачен»/«Неактуально» или восстановление источника возвращает самостоятельно не удалённые планы, если источник больше не помечен paid/inactive и не находится в корзине; собственная неактуальность плана сохраняется. Другие статусы источника, планы без источника, отсутствующий прежний источник и неизвестные отметки сохраняют прежний показ. Это только состав `calendar_invoice_plans`, без изменения схемы, файлов, фактических финансов или заказов.

У состояний `issued` и `external` есть кнопка планирования оплаты. `/api/invoice-plan-source` возвращает подпись, версию и сумму: `data.total` созданного счёта в целых копейках; у внешнего — итог PDF из неизменяемого BLOB SQLite. Swift-помощник `pdf_preview.swift` в режиме `invoice-text` читает текст PDFKit, для сканов использует локальный Vision OCR первых двух и последней страницы. Просматривает первые 20 и последние три страницы, ограничивает текст и время. Парсер принимает однозначный денежный итог с подписью («Итого к оплате», «Всего к оплате», «Итого» и др.); противоречивый/нечитаемый итог оставляет ручной ввод с пояснением. Суммы строк, реквизиты и сумма заказа не подменяют итог счёта. Технический кеш текста по SHA-256 в `data/invoice-amounts` не является рабочей записью; каждый запрос заново проверяет UUID, путь и корзину через SQLite. Ни iCloud, ни внешние сервисы для чтения не используются.

При создании плана по счёту обязательны UUID и версия источника; в JSON плана сохраняются `invoice_id` и `invoice_label`. Новый план по готовому счёту по умолчанию `incoming` («+ Получить оплату») и для `issued`, и для `external`: прикреплённый PDF может быть собственным счётом пользователя. Расход `outgoing` выбирается явно; способ добавления PDF не определяет направление денег. При редактировании сохраняется выбранное направление существующего плана. Можно планировать несколько частичных оплат с ручной суммой. Интерфейс группирует активные планы по `invoice_id` и пути внутри строки исходного `issued`/`external`: каждая дата и сумма — отдельная кнопка правки с собственной корзиной, без дополнительной строки и увеличения счётчика. Сами планы сохраняют UUID, версии, историю и отдельные маркеры календаря; переноса данных не требуется. Если исходного счёта нет в активном списке, план показывается отдельно, чтобы не потерять доступ. Источник, PDF, номера, комментарий и фактические финансы неизменны; поздние правки, перенос и отметки плана сохраняют связь. При конфликте проверка актуального счёта сохраняет введённые поля. Переименование заказа переносит план обычным механизмом `invoices`, UUID счёта не меняется.

«+»/«−» шапки дня открывают общий редактор оплаты без заказа: дата, направление, сумма и строка `text` до 500 символов. Выбор и загрузка списка заказов из формы удалены, новый календарный план всегда имеет пустой `path`. Шапка дня: две равные колонки поступлений и расходов, каждая оплата отдельной строкой 12 пикселей с полной суммой и короткой серой подписью (название заказа, а без заказа — комментарий или вид оплаты; многоточие при нехватке места). Справа отдельная дата: «+»/«−» над числом. Планы выписки показаны строками в колонке поступлений: зелёный `+ ****`, затем серым название заказа; отдельной колонки маркеров нет. Количество строк оплат и планов выписки не ограничивать, внутренней прокрутки шапки нет. Высота недели увеличивается на рост шапки сверх прежних 32 пикселей; область событий сохраняет высоту и строки. Область календаря равна сумме высот двух видимых недель. Прокрутка, стрелки, Home/End, «Сегодня», опрос и изменение размера используют фактические высоты недель и сохраняют видимую неделю, фокус и внутреннюю прокрутку. Статичную подпись «События» в левой колонке не показывать; пустая ячейка сохраняет выравнивание свободных событий. Для записи без заказа используется та же таблица `invoices`, `state=planned`, `path=""`, `data.scope="calendar"`, остальные поля JSON версии 1 прежние. Создание без заказа не допускает операцию выписки счёта; обычные счета по пустому пути недоступны. Путь существующего плана не перепривязывается. Свободные планы входят в календарь независимо от списка заказов, редактируются нажатием на сумму и сохраняют общую отметку «Неактуально» с версиями/историей. Планы с заказом открывают его карточку. Суммы не объединяются; комментарий и подпись счёта показаны в подсказках. У сумм «+»/«−» без заказа всплывающая подсказка содержит только сохранённый комментарий, без действия, суммы, даты, «Без заказа» и отметки актуальности. При пустом комментарии подсказки нет. Полное доступное имя `aria-label` сохраняется; у планов с заказом прежняя подробная подсказка. Дополнительные данные и отсутствующий в старом запросе комментарий сохраняются. Маркер `metadata_settings.invoice_payment_sources=1` после создания связи или свободного плана блокирует деплой/откат к коду без `INVOICE_PAYMENT_SOURCE_VERSION = 1`.

Планы выписки и оплат хранятся в той же `invoices`, состояние `planned`, без PDF/имени файла/очереди публикации, `year=0`, технический `number=UUID` не занимает годовую нумерацию. JSON: `version: 1`, `kind: "planned"`, `date: "ГГГГ-ММ-ДД"`, `operation: "invoice"|"incoming"|"outgoing"`; у оплат положительная целая `amount` в копейках до 99 999 999 999. Отсутствующая операция у формата 1 означает выписку. `/api/invoice-plan` создаёт запись по новому UUID; повтор возвращает текущее состояние без замены поздних правок и запрещён после корзины. Редактирование требует текущую целую `revision`, меняет только поля плана с повышением версии и `invoice_history` в одной транзакции. Неизвестный формат остаётся без замены и не включается в календарь. Существующие неизвестные дополнительные поля сохраняются. При наличии планов деплой блокирует откат к коду без `INVOICE_PLAN_VERSION = 1`.

В колонке «На неделю» доступны те же отдельные финансовые записи, две колонки поступлений/расходов, строки выписки в колонке поступлений и «+»/«−» над ISO-номером недели. Форма планирования выбирает «На день» или «На неделю»; недельный план хранится в прежней таблице `invoices` как `data.period="week"` с датой понедельника, дневной — `"day"` (отсутствие поля у прежних записей означает день). Недельные суммы и планы выписки не дублируются в понедельник, не объединяются и имеют прежние переходы и подсказки; у самостоятельной оплаты подсказка содержит только комментарий. «+»/«−» недели создают записи без заказа, планы счёта или оплаты заказа также можно назначить на неделю. Выбор любого дня в недельной форме приводит дату к понедельнику с показом полного диапазона. Редактирование, смена дня/недели, актуальность, корзина, версии, история и защита ввода общие; пропущенный `period` при частичной правке сохраняет прежний период, неизвестный формат не заменять. Код без `INVOICE_WEEK_PLAN_VERSION = 1` при наличии недельных планов не разворачивать.

`/api/orders.calendar_invoice_plans` читает только SQLite, включает планы обычных видимых зарегистрированных заказов без влияния поиска, статуса или оплаты таблицы; производственные и неактивные ветки исключены. Каждый план — отдельная ссылка над строками своего дня: зелёная строка выписки `+ ****` с названием заказа, зелёная сумма с плюсом либо красная с минусом. Планы не меняют сроки, события, статусы и фактические суммы заказа, не объединяются при совпадении даты, заказа, вида или суммы. У каждой суммы и каждого плана выписки своя подсказка (`title` и `aria-label`): заказ, клиент, объект, действие, сумма с направлением и дата. Каждая ссылка ведёт в свой заказ. Количество строк оплат и планов выписки не ограничено. Шапка показывает две колонки поступлений/расходов и отдельную дату с кнопками сверху; планы выписки идут строками в колонке поступлений. Рост шапки добавляет высоту неделе и календарю, без внутренней прокрутки шапки и уменьшения места событий. Все девять колонок и строки заказов выровнены; прокрутка и навигация учитывают переменную высоту недель. Список и диалог сохраняют ввод при опросе/ошибке; конфликт требует явной проверки изменений. Корзина использует прежний `_trash`, без файловых операций у плана; восстановление возвращает маркер календаря. Перенос пути и откат используют общие связи `invoices`, планы не создают папок или документов.

Черновики, реквизиты, история, общая нумерация за год и неизменяемые выпущенные PDF уже хранятся в SQLite. Номер можно менять до выпуска. Счёт и краткий счёт-договор — компактный A4 на одной странице, без QR, «Без НДС». При слишком длинных данных выпуск отклоняется с сохранением черновика; текст не обрезается. Изменение выпущенного документа — новый «На основе». Статусы и финансы заказа автоматически не меняются.

Копии PDF атомарно публикуются устойчивой очередью в `# bills`, без перезаписи, с повтором через 15 секунд и после перезапуска. Форма и PDF читаются из базы без iCloud; проверяются версия, дата и путь. Переименование и откат сохраняют связи и очередь. Фоновое обновление не пересоздаёт неизменившиеся строки и не сбрасывает фокус соседних событий. Дальнейшее совершенствование выпуска счетов — отдельная работа.

Внешние PDF-счета (до 20 МБ) хранятся точными байтами в той же таблице `invoices`, состояние `external`, с исходным именем, датой прикрепления и комментарием до 5000 символов в `data`. Их копии публикуются в `# bills` той же очередью, имя получает короткий UUID-суффикс. Чужие файлы не перезаписываются. Повтор передачи того же UUID и PDF возвращает существующую запись, сохраняя поздние правки комментария; другой путь или документ с этим UUID отклоняется. Годовая нумерация созданных счетов не меняется. Общий список читает метаданные без BLOB; PDF открывается из SQLite даже при недоступном iCloud. Комментарий изменяется отдельно с обязательной версией и записью в `invoice_history`; PDF, статусы и финансы заказа не меняются. Переименование и самостоятельный откат согласуют путь и очередь как у выпущенных счетов. Прикрепление не импортирует произвольные PDF из прежних папок автоматически.

Форма внешнего счёта принимает один PDF выбором или перетаскиванием; передача начинается по кнопке «Прикрепить». Комментарий в списке показан первым, крупнее и полужирным, до двух строк; ниже имя PDF, дата/тип и состояние копии. Без комментария первым остаётся имя файла. Длинный текст доступен полностью при наведении и в просмотрщике. Заголовок строки и PDF открывают встроенный просмотрщик. Для рендера неизменяемые байты из SQLite атомарно материализуются в локальном техническом `data/invoice-previews/<sha256>.pdf`, страницы — в обычном кеше просмотра. Копия `# bills` и iCloud не читаются. Даже при готовом кеше каждый запрос проверяет UUID, путь и отсутствие маркера корзины через SQLite. Справа редактируется именно комментарий счёта (`invoice_history`, обязательная версия), а не комментарий к файловой копии. Закрытие/переключение сохраняет ввод; при ошибке окно остаётся открытым. Скачивание доступно отдельно, исходные байты и очередь не меняются.

У внешних, созданных и черновых счетов в списке есть одна ручная отметка: `active` («Актуально»), `inactive` («Неактуально»), `later` («Позже»), `sent` («Отправлен») или `paid` («Оплачен»). Выбранная кнопка подсвечена, повторное нажатие возвращает `none`; отсутствие поля тоже означает `none`. Значение хранится в `invoices.data._list_status`, ответ содержит вычисленное `list_status`. Частичное сохранение требует текущую версию и фиксирует прежнее `data` в `invoice_history` в той же транзакции. Неизвестное значение остаётся без замены, его кнопки отключены. Содержимое и байты PDF, комментарий, реквизиты, очередь копии, номера, финансы и статусы заказа не меняются. Отметка сохраняется при редактировании черновика, выпуске, переименовании, корзине и восстановлении; новый документ «На основе» создаётся без отметки. Изменение видно между окнами без потери ввода и фокуса.

Корзина счетов использует маркер `_trash` внутри `invoices.data`: случайный `token`, `state` (`pending`/`complete`) и техническая ошибка. Он записывается транзакционно с повышением версии счёта и `invoice_history` до файловых действий. Строка и BLOB не удаляются; годовой номер не освобождается. Активный список и обычная очередь выгрузки исключают маркер, отдельный список корзины читает только метаданные. PDF и прежние комментарии/история файла перемещаются в `# bills/.trash/<token>/` через журнал `file_trash`; комментарии SQLite меняют путь по `metadata_file_moves`. Скрытая `.trash` не участвует в обычном обходе вложений. Если копии ещё не было, она безопасно создаётся из SQLite перед переносом. Повтор не создаёт второй сеанс; известный завершённый перенос распознаётся по идентичности, чужие пути и изменённые копии блокируются без перезаписи. Корзина обрабатывается с обычной очередью каждые 15 секунд и после запуска.

Восстановление возвращает исходный путь PDF и комментариев, снимает `_trash` с версией и историей. При конфликте файл остаётся в корзине. Тот же переход карточки выполняется самостоятельным `.restore.py` из журнала; он не зависит от импорта приложения и не заменяет базу снимком. При наличии счёта в корзине переключение на код без `INVOICE_TRASH_VERSION = 1` запрещено: прежний код мог бы показать запись активной и повторно выгрузить документ. Автоочистки и безвозвратного удаления нет.

## Просмотр таблиц Excel

XLS/XLSX/XLSM/XLSB остаются исходными вложениями в папках документов. Просмотр только для чтения получает байты через согласованное чтение iCloud и разбирает их локально в браузере; новая рабочая запись SQLite, копия документа или внешний сервис не создаются. Макросы и формулы не исполняются, оригиналы не меняются. Комментарии файлов сохраняются отдельно по прежним правилам SQLite, включая ввод в развёрнутом просмотре. Возможности и ограничения — [в операциях](operations.md#просмотр-таблиц-excel).

## Задания на фрезеровку

Рабочие карточки заданий `# work/# freza` используют существующие `orders`, а заметки незарегистрированных и вложенных папок — `folder_notes`. Новая схема или служебный файл карточки не создаются. UUID, версии, история, задачи, комментарии и данные прежних карточек сохраняются; производство по-прежнему не входит в обычную главную. Создание нового задания проходит существующее устойчивое намерение `order_creation`, журнал и самостоятельный откат, но без шагов создания `# bills` и `# cdr`.

Изображения и CDR остаются пользовательскими файлами в папке задания; прежние вложения отображаются рекурсивно без переноса и изменения путей комментариев. Загрузка разрешена прямо в задание, включая зарегистрированное, с теми же проверками идентичности, потоком и атомарной публикацией без перезаписи. Создание событий в задании сервер отклоняет. Старые подпапки и их рабочие записи остаются доступными, автоматически не объединяются и не удаляются.

Превью загружаются лениво отдельным запросом, без чтения содержимого вложений при построении списка заданий. Для CDR используется встроенный PNG или BMP (локально преобразуется в PNG), исходник читается через `icloud_access.py` с ограничением 20 МБ, результат кешируется локально по версии файла. Файл без поддерживаемого встроенного превью или превышающий предел остаётся доступен как оригинал. Превью и комментарий файла открываются общим просмотрщиком, байты оригинала не меняются.

## Задания на печать

Единственный способ создания и ведения печати — отдельный редактор `# work/# print`; обычные заказы поставщикам здесь больше не создаются и не регистрируются. Прежние папки показываются отдельно в свёрнутом блоке, без изменения документов, UUID, зарегистрированных карточек, заметок, задач и истории. Автоматического слияния по названию нет. Новые подборки поставщиков не предлагают эти прежние папки, уже сохранённые связи остаются.

Только непосредственные прежние TXT/textClipping-задания раздела `# work/# print` импортируются в базу с точными исходными байтами. Название, ссылка и описание редактируются в черновике SQLite. Создание и сохранение черновика не создают новый файл задания или папку заказа. Вложенные документы прежних папок и выпуски не импортируются в задания, список не читает обычные комментарии файлов. Прямое обращение к выпущенному документу также не создаёт черновик.

«Выпустить в папку» фиксирует содержимое выбранной версии в `metadata_publications`. Файл `Задание - ГГГГ-ММ-ДД - <ключ>.txt` содержит название, ссылку и описание. Повтор выпуска той же версии возвращает тот же документ. Новая версия выпускается отдельным файлом. Очередь хранится в базе, повторяется через 15 секунд и после запуска. Занятый другим содержимым путь не перезаписывается; ошибка видна в состоянии хранилища. Выпущенные документы не импортируются обратно как новые черновики. Это основа хранения; расширение самого процесса печати будет отдельной работой.

## Входящие файлы из браузера

Загрузка в открытое событие копирует исходные байты в каталог документов на M4 через сервер, независимо от компьютера с браузером. Это пользовательские вложения, не рабочие метаданные SQLite. Поток проходит через скрытый временный файл в целевой папке; готовое имя появляется атомарно после полной передачи. Прежние документы и связанные комментарии не меняются, совпадения получают числовой суффикс. Имена записей базы и ожидающих копий счетов/других документов также зарезервированы, даже если файла ещё нет. Идентичность папки проверяется повторно перед публикацией; статусы, финансы, регистрация, заметки и задачи остаются прежними. Сохранение на M4 не доказывает завершение синхронизации iCloud. Ограничения и обработка ошибок — [в операциях](operations.md#загрузка-файлов-в-событие-через-браузер).

## Выбор файлов и PDF-отчёт

Выбор сохраняется при фильтрации, сбрасывается при переходе в папку. Отчёт включает только выбранные изображения и полные сохранённые комментарии из базы, остальные типы пропускаются с указанием количества. До 200 изображений, A4, сетка 2×2. Длинный комментарий занимает следующие ячейки и страницы. Изображения в отчёте — копии до 1200 пикселей, JPEG 72%, прозрачность на белом; оригиналы не меняются. Готовый `report - ГГГГ-ММ-ДД.pdf` публикуется атомарно без перезаписи с суффиксом при совпадении имени.

## Группировка заказов объекта по годам

Создание объекта не регистрирует его как заказ. Создание заказа через менеджер сразу добавляет карточку и пустые служебные папки `# bills` и `# cdr`; прежние и вручную созданные папки регистрируются отдельно. Группировка существующих заказов меняет пути всех затронутых записей одной транзакцией по правилам переименования: `orders`, `folder_notes`, сводки задач, активность, счета, `metadata_records`, импорт и очереди публикации. UUID, история, заметки, задачи, избранное, суммы и PDF сохраняются; версии повышаются. Карточки документов не переписываются.

До первого переноса сохраняются согласованный снимок SQLite, план, файловый журнал, `.folder-paths.json` со всеми парами путей и `.restore.py`. Намерение в `folder_renames` записывается устойчиво до файловых действий и защищает весь объект. При сбое выполняется согласованный откат; прерывание оставляет блокировку до восстановления. Откат согласует обратные пути с актуальной базой, сохраняет поздние правки и новые документы; созданный год с поздними файлами или данными SQLite остаётся на месте. Не заменяй рабочую базу старым снимком для обычного отката.

## Подпись поставщика в заголовке производства

Имя поставщика в крупной подписи перед названием заказа или события в разделе `# work` вычисляется только из фактического пути. Ответ карточки SQLite содержит `work_supplier` и сохранённый `work_supplier_color`, ответ открытой папки — `workSupplier` и `workSupplierColor`; чтение iCloud для подписи и цвета не требуется. Новые разделы поддерживаются автоматически; собственные датированные заказы корня не получают чужой подписи. Имена карточек, пути, статусы и финансовые данные не меняются.

## Корзина событий поставщиков

Пока удаление доступно только для непосредственных обычных событий заказов поставщикам в разделах `# work` (кроме `# print`) и прежней корневой `# glass`. Удаление заказа и событий обычных заказов отложено. После подтверждения пути и количества вложений вся папка атомарно перемещается в `.deleted-event-<UUID>` внутри её прежнего родителя. Байты файлов и старые служебные данные сохраняются. Проверка состава использует только метаданные файлов, без чтения содержимого вложений; изменение файлов, папки или версий заметок после подтверждения требует открыть форму заново.

До переноса сохраняются согласованный снимок базы, план, журнал, самостоятельный `.restore.py` и устойчивое намерение в `folder_renames` с типом `supplier-event-trash`, токеном и исходным/скрытым путями. Общая транзакция переносит пути SQLite с повышением версий и историей; заметки, задачи, комментарии, черновики и очереди не удаляются. Скрытые пути исключены из сводок задач, списков заказов и публикации документов. Прерывание оставляет пути заблокированными до согласованного восстановления.

Кнопка «Корзина событий» в заказе и общая «Корзина» показывают события, включая прерванные операции. Кнопка событий использует отдельный запрос только к SQLite, без обращения к каталогам и журналам iCloud. Общая корзина читает события независимо от файловых журналов: недоступный журнал не превращает список в пустой и не скрывает остальные записи; показывается предупреждение о неполноте. Журналы читаются через ограниченный `icloud_access.py` с восстановлением доступа Foundation и таймаутом, без чтения содержимого удалённых вложений. Восстановление возвращает папку и пути базы без перезаписи новых файлов или данных. Переименование предка требует сначала восстановить события и файлы из его корзины. При наличии активных операций такого типа код без `EVENT_TRASH_VERSION = 1` не допускается к базе. Безвозвратного удаления и автоочистки нет.

## Переименование и корзина

Переименование в менеджере меняет пути заказов, заметок, активности, комментариев, черновиков, очередей документов и каталога задач в одной транзакции. История и идентичности сохраняются. Журнал и самостоятельный откат согласуют обратный перенос с SQLite. Прежние рецепты отката переименований обновляются до поддержки нового хранения; исходные байты скрипта предварительно архивируются в базе. Прерванные пути блокируются до восстановления. Переименование отдельного файла в Finder автоматически не переносит его комментарий.

Удаление выбранных файлов требует подтверждения полного списка. Обычные файлы, старые комментарии и история перемещаются в `.folder-layout-history/.file-trash` без изменения байтов. Комментарий базы перемещается на путь файла в корзине. Устойчивое намерение в базе и файловый журнал позволяют восстановить прерванную операцию; незавершённый перенос блокирует запись комментария. Самостоятельный `.restore.py` использует исходную SQLite и не создаёт пустую базу, если она потеряна. Новые файлы или комментарии по исходному пути не перезаписываются, восстановление останавливается при конфликте. Автоматической очистки нет.

## Резервные копии и восстановление

В `data/backups` создаются согласованные SQLite-снимки через `Connection.backup`: перед первым переносом дня и ежедневно после прохода. Каждый снимок проверяется `PRAGMA quick_check`, затем публикуется атомарно. Автоматической очистки нет. Отдельный снимок создаётся деплоем перед переключением релиза. Это локальные копии на M4. По решению пользователя от 23 октября 2026 года дополнительный ежедневный бэкап помещается в скрытую `.manager-backups` непосредственно в корне «Зигзаг» в iCloud Drive. Рабочая база по-прежнему локальная: синхронизируются только неизменяемые ZIP-снимки.

Самостоятельный ZIP `backup-ГГГГ-ММ-ДД-ЧЧММСС-<id>.zip` содержит всю SQLite (`manager.sqlite3`, включая PDF счетов, истории и очереди), исходники работающего приложения `application/`, `manager.ini`, справочную копию LaunchAgent при наличии, `manifest.json` с путями/временем/числами строк/SHA-256, `RESTORE.txt` и автономный `verify.py`. Не включает технические кеши, старые релизы и обычные пользовательские вложения. Для полного восстановления сохранять также весь каталог «Зигзаг», включая `.folder-layout-history` и другие скрытые журналы/корзины: они уже находятся в iCloud и не дублируются в ежедневном ZIP.

Отдельный обработчик `recovery_backup.py` работает независимо от миграции: первая копия сразу при запуске, затем первая проверка нового календарного дня по `Europe/Moscow` (опрос раз в 60 секунд). Выключенный M4 или остановленный сервис не делает копий; при следующем запуске создаётся копия текущего дня. SQLite снимается через `Connection.backup`, переводится в самостоятельный DELETE-снимок без WAL/SHM, проверяется `PRAGMA integrity_check` и состав/число строк всех таблиц. До публикации проверяются SHA-256 каждого файла и целостность ZIP, после копирования — SHA-256 ZIP. В iCloud сначала скрытый временный файл, затем атомарное имя без перезаписи; ошибка не считается успехом, повтор через 60 секунд и после запуска. Старые резервные копии автоматически не удаляются. Запись в папку iCloud на M4 не подтверждает доставку в облако или на другой компьютер.

Локальное состояние `data/orders-<root-hash>-recovery-backup.json` фиксирует только завершённую копию, дату, путь, SHA-256, размер и последнюю ошибку. Обычный фоновый опрос состояния читает только локальный файл, не iCloud; на главной показаны последняя копия или ошибка с автоповтором. На день/корень не создаётся повторный архив, кроме явного `--force`; дополнительный снимок также не заменяет предыдущие. Инструкция проверки и восстановления — [в операциях](operations.md#резервная-копия-в-icloud-и-восстановление).

**Базу необходимо сохранять всегда**, даже после успешного выпуска всех документов. Каталоги с PDF и прежними `!.txt` не восстанавливают новые заметки, комментарии, задачи, черновики, нумерацию и историю. Для восстановления остановить сервис, сохранить повреждённую базу вместе с WAL/SHM, выбрать проверенный снимок и восстановить его отдельно по инструкции обслуживания. Старую копию нельзя автоматически накатывать поверх актуальной базы.

Откат на код без поддержки `local_metadata.py` заблокирован после перехода базы на новый режим. Обычный деплой сохраняет текущую базу и документы. Обновление рабочего кода не требует замены базы снимком.

## Обмен с iPhone

По решению пользователя обмен отложен. Обработчик не читает и не публикует iCloud-обмен, включение недоступно. Прежние идентификаторы, настройки, действия и очередь сохраняются. Исходники `mobile/` остаются для будущей доработки; совместимость протокола с новым хранением и испытание реального iCloud потребуют отдельной работы.
