# SQLite и форматы: что именно хранится

## Соединение и файл базы

Файл `orders-<hash>.sqlite3` выбирается абсолютным корнем документов. `OrderStore.connect` использует отдельное соединение, `sqlite3.Row`, timeout и WAL. WAL позволяет читателям видеть согласованный снимок во время записи, но не превращает SQLite в базу с несколькими одновременными писателями. `-wal` и `-shm` — часть живого состояния; обычное копирование только основного файла не заменяет backup API.

Схема создаётся и расширяется рядом с соответствующим адаптером, отдельного общего каталога миграций нет. `CREATE TABLE IF NOT EXISTS` не добавляет новый столбец в уже существующую таблицу: для этого код проверяет `PRAGMA table_info` и выполняет предусмотренный `ALTER TABLE`. После изменения полей аудит-триггеры иногда необходимо пересоздать, чтобы история включала новый столбец.

[Полный DDL-справочник](../reference/sqlite-schema.md) извлечён статически из строк SQL. Динамические f-string триггеры показаны как шаблоны. Он не содержит рабочих строк, персональных данных или утверждения, что каждая таблица уже есть в конкретной базе M4.

## Семейства данных

| Группа | Содержимое |
| --- | --- |
| `orders` | Зарегистрированные и сохранённые снятые регистрации, UUID, путь, версия, статусы, копейки, заметка, JSON блоков |
| `folder_notes` | Карточки произвольных папок, связь с родительским заказом, версии и состояние первоначального импорта |
| `metadata_records` | Типизированные записи `(kind, path)`: комментарии, черновики, каталоги, Inbox, запросы команд и настройки разделов |
| `metadata_settings` | Версия хранения и признаки использования несовместимых форматов |
| `metadata_history` | Предыдущее состояние UPDATE/DELETE для подключённых к аудиту сущностей |
| `legacy_documents`, `metadata_imports` | Исходные байты и контрольный хеш, успешность/ошибка импорта по виду и пути |
| `metadata_publications`, `metadata_file_moves` | Неизменяемые документы к публикации и состояния файловых переносов |
| `client_activity`, `object_activity` | Индексы активности путей, а не вычисляемая галочка выполнения события |
| `todo_catalog`, `todo_missing_folders` | Кеш сводок вложенных задач и доказанно отсутствующие пути |
| `invoices`, `invoice_history`, `invoice_settings`, `invoice_sequences` | Черновики/выпуски, BLOB PDF, история, реквизиты и нумерация |
| `invoice_documents` | Вложения/закрывающие документы счетов и состояние их копий |
| `calendar_events` | Свободные события; заказные тексты находятся в `orders.extra_blocks` |
| `reconciliations`, `reconciliation_invoices` | Собственные сверки и единственное назначение каждого счёта |
| `mobile_*` | Сохранённый протокол телефона; наличие таблиц не означает включённый обмен |
| `thumbnails`, `worker_status` | Отдельная база производных превью, не таблицы рабочего реестра заказов |

У специальных операций есть дополнительные таблицы журналов, перечисленные в DDL-справочнике. Их не следует очищать по правилу «это всего лишь кеш»: например, запись незавершённого rename защищает путь от противоречивой правки.

## Ключ, идентичность и версия

`path` отвечает на вопрос, где сущность находится. UUID отвечает, какая это сущность. Revision отвечает, какое её состояние видел пользователь. При корректном переименовании путь меняется, UUID сохраняется, revision повышается.

У `metadata_records` первичный ключ составной `(kind, path)`, а `id` уникален. Разные виды могут использовать один путь и иметь независимые версии. [MetadataStore.record](../../local_metadata.py#L91) возвращает revision строкой `UUID:число`; отсутствие комментария имеет sentinel `missing`. У заказа revision — целое число. Эти форматы нельзя приводить к одному числовому типу на клиенте.

`UPDATE ... WHERE ...` с проверкой ожидаемой записи выполняется в защищённой транзакции. Параметры передаются отдельно: `db.execute(sql, (value,))`. Запятая в одноэлементном tuple существенна. Имена таблиц нельзя параметризовать `?`, поэтому динамическое имя в внутренних схемах должно происходить из доверенного набора кода, а не HTTP-поля.

## JSON внутри SQLite

`orders.extra_blocks` — JSON-объект, значения которого часто являются строками прежних читаемых блоков. Некоторые строки сами содержат строгий JSON. Поэтому возможны два уровня разбора:

```text
SQL TEXT extra_blocks
  → json.loads
  → словарь «имя блока» → строка
  → строгий парсер конкретного блока
  → список дат / флаг / события
```

Это сохранённая совместимость с карточками; SQLite JSON не заменяет прикладную валидацию. Контракт проверяет version, точный набор полей, типы, сортировку/уникальность ключей и реальность дат. Неизвестная версия не должна записываться обратно как версия 1 с пустым содержимым.

Планы платежей используют JSON `invoices.data` и независимые `_calendar_*` ключи. Добавление календарной отметки не означает автоматического создания нового SQL-столбца, изменение суммы или фактической оплаты.

Сводки `calendar_events`, `calendar_invoice_plans` и `calendar_supplier_orders` в API — представления. Они не доказывают наличие таблицы с точно таким же названием: часть информации вычисляется из заказов и счетов.

## История

[audit](../../local_metadata.py#L45) получает список столбцов через `PRAGMA table_info`, создаёт BEFORE UPDATE/DELETE триггеры и сохраняет JSON прежней строки. Это охватывает также самостоятельный SQL-инструмент, если он работает с той же таблицей и включёнными триггерами. INSERT не является прежним состоянием и этим механизмом не записывается как обновление.

История и резервная копия решают разные задачи. История помогает восстановить поле/операцию, снимок — согласованную базу целиком. Ни один механизм сам по себе не отменяет уже отправленный Telegram-документ или чужое ручное перемещение файла Finder.

## BLOB и публикация

Байты PDF и вложений хранятся в SQLite, поэтому выпущенная версия воспроизводима даже при временно недоступной копии в `# bills`. Сохранённый filename не даёт права перезаписать одноимённый файл пользователя. Публикация проверяет существование/содержимое и фиксирует результат; ошибка оставляет ожидающее состояние.

[MetadataStore.publish](../../local_metadata.py#L252) задаёт уникальность `(source, revision)`. Повтор выпуска той же сохранённой версии получает ту же публикацию, а не новый документ с новым именем. Запись в очередь и физическое появление файла разделены намеренно.

[attach](../../invoice_discovery.py#L85) для уже существующего внешнего PDF проверяет точные байты и устойчивую идентичность, чтобы потерянный HTTP-ответ не привёл к двойной регистрации. Корзина не должна автоматически восстанавливаться повторным прикреплением тех же данных.

## Устойчивые состояния команд

Запрос `/calendar` — запись `metadata_records kind=telegram_calendar_request`, а не отдельная таблица задач. Курсор Telegram и создание запроса сохраняются вместе. Состояния `pending`, `sending`, `complete`, `failed` имеют бизнес-смысл: переход к `sending` отделяет «можно начать» от «внешний результат мог уже случиться».

Флаг в `metadata_settings` фиксирует использование формата. `scripts/deploy_remote.py` читает эти флаги и проверяет version-константы нового/откатываемого кода. Это защита совместимости кода и данных, а не миграция самой базы обратно.

## Снимки и восстановление

`sqlite3.Connection.backup` создаёт согласованный снимок при работающем сервере. Затем `PRAGMA quick_check` проверяет его структурную целостность. Эта проверка не доказывает бизнес-корректность всех сумм или путей. Манифест с SHA-256 отдельно обнаруживает изменение байтов копии.

Резервное восстановление требует остановленного сервиса и сохранения текущего состояния перед подменой. Обычный откат релиза оставляет актуальную SQLite. Самостоятельные рецепты миграций часто восстанавливают лишь определённые поля с проверкой поздних правок; их нельзя заменять старым снимком целиком без разбора.
